# OpenCutter: architecture and module contract

OpenCutter is a free (GPL-3.0-or-later) Linux desktop app that sends SVG designs to **Silhouette cutting machines** over **Bluetooth LE**. It is tested on the CAMEO 4 (firmware V5.xx). It also drives the models whose machine profiles are not yet tested, and it only names the models it recognizes but cannot drive (see "Machine profiles"). It is not affiliated with Silhouette America.

This file is the **contract** between the modules. Every module implements exactly the public names below, and every module may rely on the others implementing them. If a module needs something not listed, add it inside its own package and document it here under "Additions".

- Python ≥ 3.12. The GUI uses the system PyGObject (GTK 4, libadwaita 1).
- Dev venv: `.venv`, created with `--system-site-packages` so that PyGObject comes from the system. It contains bleak, dbus-fast, svgelements and pytest.
- Run the tests with `.venv/bin/python -m pytest -q`.

Related documents:
- [docs/PROTOCOL.md](docs/PROTOCOL.md): the Bluetooth protocol as OpenCutter uses it. GATT characteristics, write rules, replies, how the model is detected, the commands OpenCutter emits with their ranges, the job structure, the stop sequence and the never-send list (sections 1 to 10, shared by every model), then each model's values (sections 11 to 17). Read it before changing anything in `machines`, `device` or `job`.
- [CONTRIBUTING.md](CONTRIBUTING.md): rules for contributions, including what must never enter the repository.
- [README.md](README.md): install, first run, safety notes for users.

## Facts confirmed on a real machine

These were observed on one CAMEO 4 (firmware V5.05) on 2026-11-16, with the fixed test programs of the project's earlier reference prototype. OpenCutter reproduces their bytes exactly (`tests/test_job_builder.py`), and OpenCutter itself has since sent SVG designs to that machine and cut them, end to end (README.md, "Status").
- The first coordinate is the feed (rollers), the second is the carriage.
- Positive feed means the mat goes in. Positive carriage moves to the user's right.
- Origin is at the top-left.
- 1 SU = 0.05 mm: a 508 SU square cut in vinyl measured exactly one inch.
- TG1 acts only right after a panel load.
- `U` reports `6100,6100` after TG1 on a freshly loaded mat, and the previous `Z` otherwise.
- The vinyl setting of the Basic set (AutoBlade, Speed 5, Force 10, Blade Depth 1 (0.1 mm)) cut Oracal 651 cleanly.

Not measured yet: the position of the origin against the printed mat grid, and a stop that interrupts a running cut. What ESC 09 does (it lets the planned moves, at most eight, run out with the tool down, lifts the tool, stops and drops the commands not yet run; a paused job ends about 5 s after it) and how the machine pauses, goes on and is cancelled while paused come from the analysis of the CAMEO 4's firmware only (docs/PROTOCOL.md 3.1, 8 and 9). Not tried on a real machine yet: Cancel Job during a cut, Stop Machine after a run, a lost link or a quit during a job, the owed stop after a reconnect, the write time-outs, the machine's Pause and Unload keys during a job, the app's Pause and Resume, and Cancel Job while paused.

## Safety layers

Nothing reaches the machine without passing every one of these, in order:
1. The daemon uses a Bluetooth link only after the machine's `FG` reply named a model and firmware line OpenCutter drives, tested or not yet tested ("The machine model gate" below), and from then on checks everything with that model's profile. Nothing but ESC 05 and `FG` is ever sent to any other machine.
2. The GUI enables Send only when a material is chosen (it never chooses an unverified preset for the user), the layout's machine is the detected one and the user accepted it ("Use {name}" after the layout followed another machine), the layout's mat is one that machine may use, the detected tool matches the material and the design lies inside the media and that mat's cut area (Test Cut needs all of these but the design), and it builds the plan locally, for the layout's machine and mat, before it asks for confirmation.
3. `job.validate.validate_spec` checks every value and every point of the `JobSpec`, with the profile of the machine the job names (`JobSpec.machine`).
4. `job.plan.build_plan` builds the bytes, runs each write through the job's own byte-level validator, and checks that every tool-down move starts inside the media (`check_plan_sequence`).
5. The daemon builds the plan itself from the `JobSpec` (clients never send bytes), refuses a job or program made for another model than the connected one, runs `check_plan` before anything is sent, and checks status, tools and MTU when the session opens.
6. Every write goes through `SafeLink.write_validated` (the daemon's `ble.Cameo4` is a `SafeLink`): the job's validator again, then ESC, ETX and length checks of its own and the global floor `machines.safety.check_write` for the connected profile.
7. Every write that can lower a tool (`D`, `TF`) re-reads the tools first; every step and every batch waits for an exact, fresh ready; while the machine is paused nothing is written but ESC 05 (and the user's Resume, or the stop).
8. The daemon sends the stop sequence over the session's link: when a step fails after its first write, and also before a step while the previous one may still run (`MotionSession.motion_possible`: from every motion write until the machine read ready at the end of a step and again before the next); when the client leaves or sends anything during a step; when the machine reports Cancelling after the session's first write, or leaves Pause without going on after a pause in the middle of a batch (the job ends for good; a Paused status alone never sends the stop, the session waits, and a Paused or Cancelling status after our own stop changes nothing); when a step is refused for the machine's state after the session wrote; on the stop op (with or without a session); and on SIGTERM, SIGHUP and SIGINT while motion is possible. A client that leaves between steps gets no stop: the machine read ready at the end of the step. Once the link is lost no stop can reach the machine: when it was lost while motion was possible and no stop had got through, the stop is owed to that machine's address and sent once when the same machine is linked again and passed the model gate, while the service runs (not tried on a real machine). Until then, and after a SIGKILL of the service, only the power button stops it.

Under all of these lies the registry's self-check: every machine profile is checked against the global rules when it loads, and the import fails for a profile that breaks one ("Machine profiles").

## Machine profiles

`opencutter.machines` describes every cutter OpenCutter knows, as frozen typed values, and decides from the `FG` reply which one is on the link. It is pure Python: no I/O, and it imports nothing else from `opencutter`, so every other package may import it. The docstrings of `profile.py` (every field) and `registry.py` (how a model module declares its models, and the lookups) are the detailed contract; [docs/PROTOCOL.md](docs/PROTOCOL.md) sections 11 to 17 give each model's values in prose.

### Support levels
`profile.Support`, one per profile and per firmware line:
- **TESTED**: the profile has cut on real hardware. Today only the CAMEO 4 with firmware line V5.
- **UNTESTED**: ported from Studio's machine data and the firmware analysis, with a few values from public captures and reports, never run with OpenCutter. Jobs are allowed, with no opt-in and no extra confirmation; the app does not show the level (the command line's `status` and `info` name it). A mat whose `U` reply is unknown is offered only at this level.
- **RECOGNIZED**: the model is named (`FG`, USB id or Bluetooth name), but a fact needed to move it safely is missing. It gets ESC 05 and `FG` only, its link is released and its address skipped, with the reason `wrong-model`, and the refusal names it with its reason in plain words: "OpenCutter recognizes this CAMEO 3 but cannot drive it yet: there is no known way to stop it from the computer, and it does not report which tools are loaded."

A firmware line can only narrow its profile's level (`Support.narrower`): the CAMEO 4 on firmware V1.xx is UNTESTED. `Support.jobs_allowed` is true for TESTED and UNTESTED.

### The values
- `MachineProfile` (a model OpenCutter drives, TESTED or UNTESTED): `id` (`JobSpec.machine`, `Program.profile_id`, presets and settings: `"cameo4"`), `name` ("CAMEO 4", in every text), `support`, `identity` (`Identity`: exact `FG` model texts, `FirmwareLine`s, USB ids, Bluetooth name prefixes, `FG` texts shared with other models), `holders` (`Holder` with `Tool`s per ESC 15 code: `blade`, `depth`, `usable`, `action`), `ranges` (`Ranges` of `IntRange`s, in firmware units: Studio's range intersected with the firmware's), `dialect` (`Dialect`: one or two holders, `TJ` or none, the ESC 15 grammar and reply slots, whole-number speeds, expand mode), `mats` (`Mat`: key, `TG`, size, cutting area, expected `U` reply and its `UBasis`, the `FM1` header extra), `default_mat`, `status` (`StatusModel`: the ESC 05 replies and the ready, busy and load digits), `queries` (`Queries`: the ESC and text queries allowed after the gate), `stop` (`StopSequence`: ESC 09 twice and the gap), `basis`, and the limits `unit_mm`, `max_write`, `batch_bytes`, `max_coordinate_su`, `lowering_prefixes`, `fg_claims_session`, `power_cycle_to_connect`, `programs`, and `pause` and `resume` (the one write of the user's explicit Pause, ESC 07, and Resume, ESC 08, or None: never sent; only the CAMEO 4 has them).
- Its pure helpers write the model's commands as text: `mat_texts` (`TG<n> FN0 TB50,0`, plus `FM1` for an expand mat), `area_texts`, `condition_texts` (the per-holder forms on a two-holder model, the plain forms without `J` on a one-holder model), `trailer_texts`, `setting_grammar()` (every non-move command the builder may emit for it), and read replies: `parse_tools`, `holder_codes` (one code per holder; on a one-holder model the unused reply slot must read 0, else None: fail closed).
- `Mat.offered(support)`: never when RECOGNIZED; with an UNKNOWN `U` only when UNTESTED. KNOWN and INFERRED `U` replies are enforced (`Mat.enforce_u`).
- `RecognizedModel` (a model OpenCutter only names): `id`, `name`, `identity` (no firmware lines), `reason` (plain words) and `basis`; `message` is the refusal above. It has no ranges, mats or commands, so nothing but ESC 05 and `FG` can reach one.
- Every value is written by hand, in our own words, with a short comment that gives its basis ("measured on V5.05", "firmware analysis", "Studio 5.0.556 machine data" or "public captures and reports": what others have published, described in our own words, with no capture in the repository). No Studio rows, column names, syntax strings or preset tables (CONTRIBUTING.md).

### The registry
`registry.py` loads the model modules in `MODULES` (`cameo4`, `cameo4_plus_pro`, `cameo5`, `cameo5_alpha`, `portrait`, `recognized`; each declares a tuple `PROFILES`), runs `safety.check_entry` on every entry, and builds one `Index`: ids, exact `FG` texts and USB ids must each belong to one entry (a text several models may report goes in each one's `shared_fg_models`), otherwise the import raises `RegistryError`. Lookups: `entries()`, `profiles()`, `recognized_models()`, `tested()`, `enabled()` (TESTED and UNTESTED), `by_id(id)`, `enabled_profile(id)` (what `JobSpec.machine` and `Program.profile_id` must name), `by_fg_model(text)`, `fg_candidates(text)`, `by_usb_id(id)` and `ble_name_prefixes()` ("CAMEO", "Portrait", "CURIO": what discovery accepts, ignoring case). A model module imports only `.profile`, the standard library and shared values of another model module, never `.safety`, `.detect` or `.registry`. Today: 10 profiles (the CAMEO 4 TESTED on V5, everything else UNTESTED) and 12 recognized models.

### Detection
`detect.detect(reply, *, usb_id=None, index=None) -> Detection` parses one `FG` reply; the daemon never decides from the Bluetooth name and never sends ESC 11. The reply is stripped of ETX, NUL and ASCII whitespace at both ends (`fg_text`) and must be `<model> V<major>.<minor>` with nothing after the version; the model text is matched exactly and case-sensitively, never by prefix (`CAMEO 4` is a prefix of `CAMEO 4 PLUS`); a shared text names a model only with a USB id. Below TESTED, the reply must be exactly the model, the version and the firmware's four spaces, with at most one final ETX (`Detection.standard_tail`); otherwise it is UNKNOWN. The tested CAMEO 4 on V5 keeps the gate's earlier, lenient padding.
- `Detection.verdict`: `Verdict.USE` (a profile and a firmware line it drives), `RECOGNIZED` (a `RecognizedModel`, a RECOGNIZED firmware line, or a line the profile does not list), `UNKNOWN`, `NO_MODEL`.
- `Detection.profile` is set only for USE; `support` is the narrower level (USE), RECOGNIZED, or None; `tested` is true only for a TESTED profile on a TESTED line; `name`, `reason`, `message` (the plain-words refusal), `text`, `model`, `version`, `entry`, `line`.
- `device.protocol.is_tested_model(r)` is `detect(r).tested`; `model_text`, `reported_model` and `wrong_model_message` keep their wording.

### The safety floor and the self-check
`safety.py` holds the rules that hold for every model; a profile can be stricter, never wider:
- `NEVER_SEND_PREFIXES`: the firmware download path (`PW`, the S-records), the diagnostic unlocks (`FP`, so `FPG` too), the calibration and persistent writes (`FB`, `TB72`, `TB70`, `ZF`, `TA`, `TH`, `FY`, `FU`, `TD`, `TE`, `FD`, `TN`, `SC`), and `STRICTER_PREFIXES`, commands no job needs (`APS`, `ACT`, `AOC`, `TS`, `TR`, `BZ`, `BZK`, `TZ`, `TB24`, `TB124`, `TB125`, `TB1023`). Checked after the firmware's filler bytes are stripped (`bare`), and from every later letter of a command too, since the firmware starts a new command at a letter without an ETX before it (`command_starts`: `FX10,TB72` is refused); every command that starts with a lowercase letter is refused too (`is_never_send`).
- `FM` is a per-profile rule, not on the list: only `FM1`, right after the `TG9 FN0 TB50,0` of the header, in the same write, for an EXPAND mat on a profile whose data defines expand mode and whose `FG` texts are all in `EXPAND_MODELS` (the CAMEO 4 Pro and the CAMEO Pro MK-II), never to one in `NO_EXPAND_MODELS` (the CAMEO 4, 4 Plus, 5 and 5 Plus) and never with a 12-inch mat.
- ESC: before the gate only ESC 05 (and the text query `FG`); after it the profile's queries within ESC 05, 10, 15 and 16; ESC 09 only in the stop; ESC 07 and ESC 08 (`PAUSE_WRITE`, `RESUME_WRITE`, `is_pause_write`, `is_resume_write`) never as a query, in a motion write or as the stop, only alone as the profile's `pause` or `resume` (`check_profile` refuses any other bytes there). Every other code is refused (`NEVER_ESC`: 0x00, 0x11, 0x12 and 0x13 by name). Text queries lie within `READ_ONLY_QUERIES`.
- `check_write(data, profile)`: the floor under every motion write (the job validator and `SafeLink.write_validated` both run it): bytes, at most `max_write`, ETX-terminated printable commands, no ESC, nothing on the list, `TG` only of the profile's mats, `FM1` only in its place. `check_query(data, profile=None)` is the same for queries (`profile` None: before the gate).
- `check_profile(profile, pinned=())` (and `check_recognized`, `check_entry`) raises `UnsafeProfile` for a profile that breaks a rule: a query that is ESC 11, lowercase or not a read-only getter; a stop that is not ESC 09 twice or a gap outside 0..2 s; a range wider than any firmware takes (speed 30, force 40, `TJ` 10); a unit other than 0.05 mm; `max_write` above 480; a default mat not offered at the profile's level; a mat whose area reaches beyond the window its `U` confirms; `FM` outside its place; its own header, condition blocks and trailer breaking `check_write` or its own grammar; a grammar that accepts a never-send command; a pinned program write that breaks a rule; or a malformed shape. It raises (not assert), so it holds under `python -O`. The registry runs it on every entry, `SafeLink`'s profile setter on every profile it is given, and `job.validate.job_profile` on a profile that is not the registry's own.

### How the other packages use the active profile
- The daemon takes the profile from `FG` on the live link and nowhere else; `JobSpec.machine`, the plan's `profile_id` and a program's `profile_id` must equal it, otherwise nothing is sent. The GUI's choice of model is advisory: the app follows the profile the service detected and blocks Send until the user accepts it (gui, "Machine profiles in the app").
- Every function that needs a model takes `profile` and defaults to `CAMEO4`, and the old module constants (`protocol.STATUS_TEXT`, `TOOL_NAMES`, `STOP_SEQUENCE`, `MAX_DATA_WRITE`, `SAFE_*`; `builder.MATS`, `MAX_WRITE`; `validate.RANGES`, `UNSUPPORTED_TOOLS`; `daemon.BATCH_BYTES`, `SLOWEST_SU_PER_S`; `programs.PROGRAMS`; `presets.BASIC_PRESETS`) stay as aliases computed from the CAMEO 4 profile. So the CAMEO 4's bytes, step titles and texts are exactly those from before profiles: `tests/test_profile_characterization.py` freezes them, with the golden byte tests.
- Adding a model: a module with its `PROFILES` (in `MODULES`), its section in docs/PROTOCOL.md, its tests (`tests/test_machines_<family>.py`), and, to become TESTED, a report of real cuts (CONTRIBUTING.md, "Reporting a model").

## device

### `opencutter.device.protocol`
Pure. Constants (UUIDs, `ETX`, `ESC`; the same on every model) and the per-model reply, query and stop rules. Every function that needs a model takes `profile` (default `machines.CAMEO4`):
- `check_safe(data, queries=None)`: one allowed read-only query (docs/PROTOCOL.md 2.2 and 3.5). `None` keeps the CAMEO 4's allowlist; `PRE_GATE` (ESC 05 and `FG` only) is for the link before the model gate; after it, the profile's `Queries` (a `MachineProfile` is taken for its queries). The global rules of `machines.safety` hold for every set. `class UnsafeCommand(ValueError)`.
- `is_status(reply, profile) -> bool` (an exact ESC 05 reply of that model, never stripped) and `status_text(reply, profile, default="?")`.
- `parse_tools(reply, profile) -> tuple[int, ...] | None`: one code per holder, in `profile.holders` order, with the profile's grammar (one or two digits, ASCII only) and slot rule (`MachineProfile.holder_codes`). `tool_name(holder, code, profile)`, `describe_tools(reply, profile)` (with the holder labels).
- `lowers_tool(data, profile)`: whether a write holds a command that can lower a tool (`D`, `TF`) anywhere in it.
- `stop_sequence(profile)`: the stop writes; raises unless they are ESC 09 twice. The gap is `profile.stop.gap_s`.
- `evaluate_units(reply, expected=DEFAULT_UNITS_MAT, enforced=None) -> (verdict, message)`: the `U` check against the exact (a, b) pair of the mat, `expected` being a `Mat`, a pair or None. Verdicts (`UNITS_VERDICTS`): `ok`, `mismatch`, `unknown` (no numbers) and `unchecked` (a `U`-shaped reply for a mat whose `U` is UNKNOWN: logged and shown, never enforced). A missing pair with the check enforced is a `mismatch`, never `unchecked` (fail closed).
- The CAMEO 4's names, computed from its profile: `STATUS_TEXT` (`'0'` Ready, `'1'` Busy, `'2'` Load Media, `'3'` Paused, `'4'` Cancelling, `'5'` Rejected), `TOOL_NAMES` (holder → code → Studio name: 0 "No Tool Detected", 1 "Ratchet Blade", 2 "AutoBlade", 3 "Deep-Cut Blade", 4 "Kraft Blade, 2mm" in holder 1 and "Kraft Blade, 3mm" in holder 2, 5 "Rotary Blade", 6 "Punch Tool", 7 "Sketch Pen", 8 "Foil Tool" in holder 2), `STOP_SEQUENCE`, `MAX_DATA_WRITE`, `SAFE_ESC_QUERIES`, `SAFE_TEXT_QUERIES`, `MAX_QUERY_WRITE`.
- The model gate's wording, built on `machines.detect`: `is_tested_model(reply) -> bool` (`detect(reply).tested`), `model_text(reply) -> str` (an `FG` reply as people may see it), `reported_model(reply) -> str | None` (`model_text`, or None when the reply names no model), `wrong_model_message(model) -> str` (the refusal for a machine OpenCutter does not know), `TESTED_FIRMWARE` and `TESTED_MACHINE` (from `registry.tested()`), `REASON_WRONG_MODEL`.

### `opencutter.device.transport`
No bleak and no D-Bus. The transport interface (`ble.py` implements it for BlueZ; a USB transport comes later as a module of its own):
- `DeviceRef(transport, address, name, usb_id=None, details)`: frozen; `details` is left out of equality.
- `RawTransport` (Protocol): a dumb pipe with no safety logic. `ref`, `disconnected` (an `asyncio.Event`), `has_status_channel` (BLE indications: true; USB: only ESC 05 polls), `is_up()`, `connect(timeout)`, `subscribe(on_reply, on_status)`, `unsubscribe()`, `write(data)` (one acknowledged write, never split, merged or repeated), `max_write()` (BLE: the live MTU − 3), `release()` (frees a connection that is already gone, never drops a live one), `disconnect()` (drops it on purpose, writes nothing).
- `Discovery` (Protocol): `find(address, skip) -> DeviceRef` and `held_elsewhere(ref)`; it only reads the system's state.
- `PlotterUnreachable(RuntimeError)`; `BluetoothOff(RuntimeError)`: the computer's Bluetooth is off or missing (no adapter, or the machine's adapter, or every adapter, reports Powered false; not a `PlotterUnreachable`); `TransportBusy(RuntimeError)`: the transport could not take a write (BLE: ATT error 0x0E) and whether it reached the machine is unknown, so the daemon treats it as possibly sent (not a `ValueError`, which means "refused, nothing sent"); `MIN_WRITE_LIMIT = 20`.

### `opencutter.device.link`
`SafeLink(transport, verbose=False, on_status=None)`: every check between OpenCutter and one machine, the same over every transport (docs/PROTOCOL.md 2 and 8).
- **The gate.** `profile` is None on every new connection: only ESC 05 and `FG` may be sent (`protocol.PRE_GATE`), no motion write and no stop. The `FG` reply before the gate is kept (`fg_reply`, `detection`). The daemon opens the gate by setting `profile`; the setter needs an `FG` reply on this link and a `MachineProfile` that passes `machines.safety.check_profile`, allows jobs and has a valid stop (ESC 09 twice, a gap of 0..2 s), else `UnsafeCommand` and the link stays as it was. `use_detected_profile()` sets the profile `detect(fg_reply)` names with USE. `None` closes the gate.
- **Queries.** `esc_query(code)` and `query(cmd, timeout=REPLY_TIMEOUT)` through `_request`: the allowlist of the gate's state, ETX framing, one query at a time, late replies dropped by count and reset after two timeouts in a row. A query whose write is busy (`TransportBusy`) is written again after 0.1, 0.2 and 0.4 s (`BUSY_RETRY_DELAYS`); a second reply is dropped, and on a timeout a late reply is owed for every copy written. A query write without a Write Response within `QUERY_WRITE_TIMEOUT` (5 s) raises `TimeoutError`, and a reply is owed for every copy, as after a reply timeout. That is the one-shot path (session open, the one-shot ops).
- **Patient queries.** `patient_esc(code, stop=None, report=None) -> (reply, fresh)`: inside a session the daemon asks ESC 05 and ESC 15 this way (docs/PROTOCOL.md 2.8). One query at a time, never given up while the link is up: a write without its Write Response is reported once after `QUERY_WRITE_TIMEOUT` and waited for, never written again meanwhile; a reply missing for `protocol.STATUS_OVERDUE` (7 s) is reported (once, then every `REASK_LOG_EVERY`, 60 s) and the query asked once more, every 7 s. It ends only on its reply, on `stop` (an `asyncio.Event`: the session's stop) or a lost link, both as `QueryAbandoned` (its reply is then owed). `fresh` is false when the reply may be a late one (the query was asked more than once). `no_reply_seconds()` (how long it has been overdue, from 7 s; else None), `indications_since(mark)`, `indication_age()`, `last_indication_at`, `indication_count`, `last_reply_at`, `last_write_ack_at` and `next_indication()` (a future set by the next status indication) feed the log, the ping and the waits.
- **Timed writes and quiet windows.** Every Write Response is timed: one of `SLOW_WRITE_LOG` (1 s) or more goes to `on_slow_write(data, seconds)`, and `verbose` prints every write, reply, dropped reply and indication with its time. No query is written from the stop's first byte until `STOP_QUIET` (0.3 s) after its last, nor for `RESUME_QUIET` (0.3 s) after a Pause or Resume write (docs/PROTOCOL.md 2.7).
- **Motion.** `write_validated(data, validator)`: the caller's validator, then bytes only, no ESC, ETX at the end, no motion before the gate, nothing while the transport's limit is below `MIN_SESSION_WRITE_LIMIT` (32: MTU − 3 ≥ 32), at most `min(480, profile.max_write, write_limit())` bytes, and `machines.safety.check_write` for the profile. Never repeated: `TransportBusy` reaches the caller, and so does `TimeoutError` when the write got no Write Response within `MOTION_WRITE_TIMEOUT` (10 s; whether it arrived is unknown, so the daemon sends the stop). Cancelling a write here does not cancel it in BlueZ, so a stop after such a write may still wait behind it there. The time-outs are generous bounds, not measured. `write_limit()` and `refresh_write_limit()` give the transport's raw limit (MTU − 3; `MIN_WRITE_LIMIT` until measured); `motion_limit()` the longest write it sends now (0 before the gate or below 32).
- **The stop.** `emergency_stop()`: the profile's stop (`protocol.stop_sequence`), `profile.stop.gap_s` apart, each write alone, each with `STOP_WRITE_TIMEOUT` (2 s; a timeout is reported as "no Write Response within 2 s"); it never waits for the query lock, and a caller that arrives while it is sent shares it and gets its result (`stop_in_flight` says beforehand whether a call would). `stop_sequences` counts the sequences this link sent, and `last_stop_report` says what each write of the last one did, with its time. Before the gate it sends nothing and says so.
- **Pause and Resume.** `pause()` and `resume()`: the profile's `pause` (ESC 07) or `resume` (ESC 08) write, once, alone, for the user's explicit request; `UnsafeCommand` (nothing written) before the gate, on a profile without it, on a profile or firmware line that is not TESTED (the link's `FG` detection) and while a stop is being sent; `TimeoutError` after `COMMAND_WRITE_TIMEOUT` (2 s) without a Write Response, and any other write error as it is: never written again. `pause_writes` and `resume_writes` count them.
- **Status changes.** `on_status_change(old, new, source)` (an attribute and a constructor argument) is called when `last_status` changes, from an indication (`source` "indication") or an exact ESC 05 reply ("ESC 05"); never raises into the link.
- `machine` (the model text, set by the daemon once the gate passed), `last_status`, `transport_up()`, `disconnected`, `device` (the transport's ref), `open()`, `close()`, `release()`, `disconnect()`.

### `opencutter.device.ble`
BlueZ, through bleak and dbus-fast (docs/PROTOCOL.md 1):
- `find_bonded_cameo(address=None, skip=())`: the first device that BlueZ reports `Paired` (or `Bonded`), whose name starts with one of `machines.ble_name_prefixes()` (CAMEO, Portrait, CURIO; any case) and that offers the vendor service; with `address`, that device without the name and service checks. Never one whose address is in `skip`. It only reads BlueZ's objects; the model is decided later by `FG`. It raises `BluetoothOff` (re-exported here) when BlueZ lists no adapter, when the machine's adapter reports Powered false, or when no machine is found and every adapter is off. `bluetooth_off_error(e)` is true for `BluetoothOff`, BlueZ's `org.bluez.Error.NotReady` and bleak's `BleakBluetoothNotAvailableError`; the daemon maps all of them to the reason `no-bluetooth`. `BleDiscovery` is the same as a `transport.Discovery` (`held_elsewhere`: BlueZ reports it Connected); `device_ref(device)`.
- `BleTransport(device)`: the `RawTransport` for BlueZ: one ATT Write Request (with response) per write, the reply and status indications, the live MTU, ATT error 0x0E as `TransportBusy`. After a connect timeout it tries again only when another full attempt (`CONNECT_ATTEMPT`, 30 s) still fits before the deadline, after `CONNECT_RETRY_WAIT`; otherwise `PlotterUnreachable` at once.
- `Cameo4(device, verbose=False, on_status=None, on_status_change=None)`: the daemon's link, a `SafeLink` over a `BleTransport` (the name stays from when the CAMEO 4 was the only machine). `client` is bleak's `BleakClient`, and every write goes through it; setting `machine` opens the gate with the profile that the link's `FG` reply names when the daemon did not set `profile` itself. `ble.BleakClient` and `ble.MessageBus` stay patchable for the tests. An object made without `__init__` (the tests' bare write guards) checks with the CAMEO 4's profile.

### `opencutter.device.programs`
The fixed test programs `dry-run`, `pen-test` and `cut-test`, per machine profile: only the CAMEO 4 has them. Their bytes are pinned, and each pinned write is checked at import against a strict grammar, a small test area and the global rules for its profile (`machines.safety.check_profile(profile, pinned=...)`). `PINNED_PROGRAMS` (a `PinnedPrograms` per profile id) and `PROGRAMS_BY_PROFILE`; `build_program(name, options, profile=CAMEO4)` raises for a profile without programs ("there are no test programs for the ...").

### `opencutter.device.daemon`
`async serve(address: str|None, verbose: bool, force: bool=False, idle_exit: float=0)`. Its protections:
- the private runtime directory `$XDG_RUNTIME_DIR/app/<app id>` (see "The background service" below), checked before the locks are taken and the socket is created;
- the flock on `opencutter.lock` in that directory, the flock on `$XDG_RUNTIME_DIR/opencutter.lock` (where builds before 0.1.0 locked), and the flock on `$XDG_RUNTIME_DIR/cameo4.lock`, the lock of the legacy prototype daemon, so that neither daemon can run next to the other. Two programs must never drive the machine at the same time: whoever still runs the legacy prototype daemon stops it before starting OpenCutter, then switches the machine off and on (it accepts a new Bluetooth connection only after power-up). OpenCutter's daemon does not start while that daemon runs, and that daemon does not start while OpenCutter's runs;
- the socket `opencutter.sock` in the runtime directory, mode 0600;
- refusal to join a link held elsewhere, at startup and when reconnecting after a drop (unless `--force`);
- the machine model gate on every new link: `FG` right after the first ESC 05, and nothing more for a machine whose `FG` reply names no model and firmware line OpenCutter drives (see "The machine model gate"); everything after the gate is checked with the connected model's profile;
- a job, a plan or a program made for another model than the connected one is refused before anything is sent;
- signal masking while stopping;
- a stop on client EOF or any byte during a step, and on SIGTERM, SIGHUP or SIGINT while motion is possible (a step runs, or `MotionSession.motion_possible`), only through a usable link to the session's own machine;
- exact reply grammar;
- the pre-step ready wait (a brief Busy left over from the previous step is waited out for up to `PRE_STEP_WAIT`, 10 s of Busy replies, but not after a stop request, an unload or a cancel; a paused machine is waited for with no limit);
- the tool re-check before any write that can lower a tool;
- for a job, a refusal after the U check unless the reply is the mat's expected pair (`6100,6100` for the CAMEO 4's 12 × 12 in mat); for a mat whose `U` reply is UNKNOWN (UNTESTED models only), a `U`-shaped reply is logged and shown (`unchecked`), and a missing or malformed one still refuses the job;
- once the header went out, a `2` (Load Media) status (the profile's load digit), as an indication or an ESC 05 reply, means the mat was unloaded: a step under way ends with the stop (`MEDIA_CHANGED_STEP`), and every later step is refused with nothing more sent (`MEDIA_CHANGED`);
- once the header went out, a Paused status (`protocol.PAUSED`; `3` on every model today) that the machine reports while no stop of ours was asked for, from an indication or an exact ESC 05 reply, starts a pause (`MotionSession.paused`, `paused_at`, `paused_mid_batch`, `seen_since_pause`): the session writes nothing but ESC 05 (no chunk, `U` or ESC 15; each is checked again under the query lock right before it is written), every `PAUSED_POLL` (2.5 s) and at once on every status indication, with no time limit (`_wait_while_paused`). The pause ends on Busy (it goes on); on Ready when the pause came between batches (`batch_open` false) or within `RESUME_WINDOW` (5 s) of the user's Resume (it went on with nothing left; after a pause between batches a fresh ready is read before the next batch); on Ready after a pause in the middle of a batch with no Busy or Cancelling seen as `LEFT_PAUSE_MARK` in `MotionSession.interrupted` (maybe a cancel on the panel whose Cancelling was missed: the job ends with the stop and `LEFT_PAUSE`); on the load digit as an unload; on a stop request or a lost link. A `U` that timed out while a pause came is asked once more after the machine goes on;
- a Cancelling status (the profile's terms, `protocol.INTERRUPTED_TERMS`; `4` on every model today) that the machine reports after the header while no stop of ours was asked for is latched in `MotionSession.interrupted`, from an indication, an ESC 05 reply or the link's `last_status`: the step under way ends with the stop even when a later ESC 05 reads ready, and the next step is refused before any query, with the stop. A Paused or Cancelling status after our own stop changes nothing; Rejected and other digits are not latched (the ready waits judge them);
- no abort on silence: inside a session ESC 05 and ESC 15 go through `SafeLink.patient_esc` (`_session_query`); a step ends only on ready, a status that ends it, the stop, a lost link, or `READY_TIMEOUT` (120 s plus the batch's travel at the slowest speed) and `PRE_STEP_WAIT` counted over Busy replies only, each adding at most `BUSY_CREDIT_MAX` (1.4 s), so neither silence nor a pause uses them up. A ready reply ends a wait only when it is fresh (it answers the one query outstanding); otherwise ESC 05 is read once more. Overdue queries, unacknowledged query writes and slow Write Responses are logged;
- the user's Pause and Resume (`_command_op`, the pause and resume ops): only for an explicit request, only while a session of ours runs on the session's own usable link, no stop was asked for and the job is not ending, only on a TESTED profile and firmware line whose profile has the write (the CAMEO 4 on V5), and only after a fresh ESC 05 read under the query lock (within `RESUME_LOCK_WAIT`, 3 s): Resume while the session waits on a paused machine and ESC 05 reads Paused, Pause once the session wrote, while it is not paused and ESC 05 reads Ready or Busy. One write, never repeated; the query lock is held for its quiet window, then ESC 05 is read for up to `RESUME_CHECK` (5 s). The session then goes on, or waits, as for the machine's own Pause key;
- a stop request is honoured in every wait (the ready waits, the pre-step wait, the U check) and once more before a step reports ok: a step never reports ok after a stop;
- `MotionSession.motion_possible`: set by every motion write, cleared only when the pre-step ESC 05 reads ready (the second ready since the previous step's motion). While it is set, a failure (a lost link included), the end of the service and a refusal of the next step for the machine's state send the stop, not only while a write is in flight;
- the owed stop (`state["stop_owed"]`, by address): when a stop fails (a session's or the stop op's), when the link is lost while motion is possible and no stop got through, or when the stop op comes without a link while motion is possible, the stop is owed to that machine. When a new link to the SAME address passed the model gate, the daemon sends the profile's stop once (`emergency_stop`, ESC 09 twice), before `state["c"]` is set, so nothing else can use the link first; it is cleared on success (or by any later stop to that address that gets through) and kept for the next link when it fails. It never goes to another address, and it lives only as long as the service. While a stop is owed, `FG`'s reply is waited for `FG_TIMEOUT_OWED` (10 s) instead of 3 s on that machine's new link. Not tried on a real machine.

**Socket protocol.** JSON lines.
- One-shot ops, one request per connection:
  - `{"op":"ping"}` → `{"ok","connected","status","motion","device":{"name","address"}|null,"reason","model","stopping","version","build","api","pid","started_by"}`. `connected` is true only for a link that passed the model gate. `reason` says why there is no link (null while connected or not known): `"held-elsewhere"` (another program holds the machine's link, seen at two looks in a row; the daemon does not join it), `"not-paired"` (BlueZ knows no paired CAMEO), `"no-bluetooth"` (BlueZ cannot be reached on the system bus at all: Bluetooth is not running, or a Flatpak has no `org.bluez` permission; or the computer's Bluetooth is switched off or has no adapter, `ble.bluetooth_off_error`), `"unreachable"` (the machine does not accept a connection: switch it off and on; also when `FG` does not answer), `"wrong-model"` (the machine's `FG` reply names no model and firmware line OpenCutter drives: a recognized model, an unknown one or no model; its link was released and it is not used). `held-elsewhere`, `not-paired` and `no-bluetooth` are cleared as soon as a look finds the machine free, before the (possibly long) connect; `unreachable` stays until a connect works; `wrong-model` stays until a machine passes the gate (or another reason replaces it). `model` is what the machine reports itself as (its `FG` reply through `protocol.model_text`: printable ASCII, at most 40 characters, but still text from the machine: escape it before using markup): that of the connected machine, or of the last refused one while the reason is `wrong-model` (null when that machine's reply named no model, `protocol.reported_model`); null otherwise. `stopping` is true once the service is ending (the shutdown op was accepted, the idle time is over, or a signal): it still answers while it releases the link (at most 5 s), but `connected` false then is not a dropped link, and the service must not be used. `version`, `build`, `api` and `pid` say which service this is (see "The background service"); `pid` is in the service's own PID namespace (in the Flatpak, its own sandbox's). `started_by` is the run id of the app that started it (`$OPENCUTTER_STARTED_BY`, `identity.RUN_ID`), or null. Clients must accept a reply without these six (an older daemon), and every reply may gain keys: clients ignore keys they do not know.
  - `{"op":"ping","machine":true}` → the same reply plus `daemon.PING_MACHINE_KEYS`: `profile` (the machine profile's id), `support` (`"tested"`, `"untested"` or `"recognized"`) and `refused_reason`. While a machine is connected: its profile id, and the narrower of its profile's and its firmware line's level; `refused_reason` null. While a recognized model is refused (reason `wrong-model`): its id, `"recognized"` and `Detection.message` ("OpenCutter recognizes this ... but cannot drive it yet: ..."). Otherwise, also for a refused model OpenCutter does not know, all three are null. The plain ping keeps exactly its keys (clients and tests compare them as a whole), and a service from before machine profiles ignores the flag. A ping with `connected` false is never a usable profile, whatever `profile` says: a CAMEO 4 on an unknown firmware line is refused with `"cameo4"` and `"recognized"`.
  - `{"op":"ping","stop":true}` (also together with `"machine":true`) → the same reply plus `daemon.PING_STOP_KEYS`: `stop_owed` (bool: a stop could not get through; it is sent once the same machine address is linked again and passed the model gate), `owed_stops_sent` (int: goes up each time an owed stop went out on a new link), `motion_stopped` (bool: the open session got a stop request, from any client, for example `opencutter stop` at the outline gate), `interrupted` (why the open session ends with the stop although nobody asked: the Cancelling digit it saw after its first write, or `"left-pause"`, `daemon.LEFT_PAUSE_MARK`, when the machine left Pause without going on; null otherwise) and `load_seen` (int: how often the status changed to the load digit `2` on any link since the service started: a change means an unload, even between two pings); since API 2 also `paused` (bool: the open session waits on a paused machine), `resume_ok` and `pause_ok` (bool: a resume or pause op would be sent now, `_command_refusal`), `no_reply_s` (seconds the query the session waits for has been unanswered, from 7 s on; else null), `indication_age_s` (seconds since the last status indication, or null) and `stop_check` (the read-back of the last stop op with `check`, also while it runs: `{"running","status","seconds","still_busy","still_paused","reason"}`, or null). The plain ping and the machine ping keep exactly their keys.
  - `{"op":"shutdown"}` → `{"ok":true}`, then the daemon ends; `{"ok":false,"error"}` while a session is open or opening. Nothing is sent to the machine for it.
  - `{"op":"esc","code":5|0x10|0x15|0x16}` (the connected profile's ESC queries; any but ESC 05 is refused while the machine last read Paused or Cancelling)
  - `{"op":"query","cmd":"FG"|...}` (the connected profile's allowlist; refused while the machine last read Paused or Cancelling and for `QUERY_HOLD_AFTER_STOP`, 10 s, after a stop)
  - `{"op":"stop"}` → `{"ok","errors"}`: always sends the stop through a link that passed the model gate, with a session open (forced: sent, or joined while one is in flight) or without one (the app's Stop Machine after a run, `opencutter stop`); it never waits for the query lock. With `"check":true`, a stop that got through is followed, after its quiet window, by ESC 05 reads every 0.4 s (sooner on a status indication) for up to `STOP_CHECK` (3 s) while the machine reads Busy or Cancelling and up to `protocol.STOP_CHECK_PAUSED` (15 s) once it read Paused (each read waits at most `STOP_LOCK_WAIT`, 4 s, for the query lock), and the reply adds `status_after` (the last ESC 05 digit read, or null; the Paused digit: still paused, press Unload) and `still_busy` (true: still Busy, press the power button; null: nothing was read). A Ready reply says what the machine reports, not that no motion is left. The result is logged, with the statuses a paused machine went through (`cancel while paused: the machine read 3 for 5.3 s, then 4, then 0`), or why nothing could be read; a failed stop logs what each of its writes did. Without a usable link the reply is `{"ok":false,"error"}` as for every op below; it then also sets the open session's stop flag, and the stop is owed when motion was possible.
  - `{"op":"info"}` → `{"ok","status","tools","firmware"}`. This is a convenience op: ESC 05 and ESC 15 under the query lock, and the `FG` reply read at the model gate (it never sends `FG`: a paused machine would not answer it, and on the CAMEO 4 `FG` claims the session). While the machine last read Paused or Cancelling no ESC 15 is sent and `tools` is null.
  - `{"op":"resume"}` and `{"op":"pause"}` (API 2) → `{"ok","sent","status_before","status_after","paused","errors"}`, plus `"error"` (plain words) when nothing was sent (`sent` false: refused, see the user's Pause and Resume above) or the write failed (`sent` true: whether it arrived is unknown; never sent again). Only for an explicit click or command (the app's Resume and Pause, `opencutter resume`, `opencutter pause`); one-shot op failures (`info`, `esc`, `query`, `resume`, `pause`) are logged once until the op works again.
  - `esc`, `query`, `stop` and `info` (with `resume` and `pause`, every op that writes to the machine) and the session ops answer `{"ok":false,"error"}` without a link that passed the model gate (`resume` and `pause` with `"sent":false` and the error "the machine is not connected"): while the reason is `wrong-model` the error is `daemon.refused_message(model, reason)` (for a recognized model its plain-words reason and `daemon.RECOGNIZED_REFUSAL`, "Nothing more is sent to it."; for any other machine `protocol.wrong_model_message(model)`), else `daemon.NOT_CONNECTED`.
  - **API version.** `model`, the reason `wrong-model`, the ping's machine fields and the open reply's `profile` were additions under `API_VERSION` 1: a client that does not know them sees a machine that is not connected, and the service refuses every session and every op that writes to such a machine by itself, whatever the client. 0.1.1 raised `API_VERSION` to **2**: steps that wait with no time limit while the machine is paused, the resume and pause ops, the new stop-ping fields and `info` without `FG`. The app and the command line never use a service of another build anyway (its sessions are refused and the app replaces it), so app and service of different builds never meet here.
- Session ops, one connection per session. The client never sends bytes, only a program name or a JobSpec:
  - `{"op":"motion","program":"dry-run"|"pen-test"|"cut-test","options":{...},"build","api"}`: `programs.build_program(name, options, profile)` for the connected profile (refused for a model without test programs), and the program's `profile_id` must be that profile's id.
  - `{"op":"job","spec": <JobSpec.to_dict()>,"build","api"}`. The spec's `machine` (`"cameo4"` when absent) must be the connected profile's id, checked before anything is built ("this job was made for the CAMEO 5, but the machine is the CAMEO 4"). The daemon then calls `opencutter.job.plan.build_plan(JobSpec.from_dict(spec))`, which validates everything with that profile, and checks the plan's `profile_id` too. It then runs the same session machinery as for motion, with the session's profile (`MotionSession.profile`): its status digits, batch size and slowest speed.
  - `build` and `api` are the client's own (`opencutter.identity`): a daemon of another build or API refuses the session before anything is sent. A request without them (an older client) is not checked. Once a shutdown was accepted (or the idle time is over), every session request is refused ("the background service is stopping").
  - The open reply is `{"ok":true,"status","tools","write_limit","profile","steps":[{"kind","title","expect","confirm":bool,"writes":n,"tool_down":bool}], "summary":{...}}` or `{"ok":false,"error":...}`. `profile` is the id of the profile the session runs with. `tool_down` is true for a write step that holds a write that can lower a tool (the profile's lowering commands); always false for the units step. The session is refused at open when MTU − 3 is below 32 or a write is longer than the link sends (`SafeLink.motion_limit()`), with a log line `<name>: refused at open: ...`.
  - Then `{"op":"step","index":i}` in order → `{"ok":true,"status","seconds"}` or `{"ok":false,"error","stopped","stop_errors"}`, and finally `{"op":"end"}`. Every failure with a lost link has the error `daemon.LINK_LOST` ("the Bluetooth link was lost"); when motion was possible it also has `stopped` true with the `stop_errors` of the stop tried on the dead link, and the stop is then owed. A refusal for the machine's state after the session wrote (a stop request, Cancelling, a machine that left Pause without going on, Rejected, still Busy, an unknown digit) has `stopped` true and `stop_errors` as well. A step has no time limit while the machine is paused: clients wait for it (`Session.step(i, None)`) and watch the stop ping. The texts: `STOPPED_IN_STEP` (mid-step), `STOPPED_BEFORE_STEP` and `STOPPED_IN_UNITS` (formatted with `again=`), `MEDIA_CHANGED_STEP` and `MEDIA_CHANGED_STEP_PROGRAM` (the load digit mid-step), `LEFT_PAUSE` and `LEFT_PAUSE_PROGRAM` (it left Pause without going on), `_status_stop_text(status, sess, before_step)` (Cancelling, `LEFT_PAUSE_MARK`, Rejected and a Busy that outlasts the pre-step wait; each says to press Unload or switch the machine off; none tells to press Pause; a Paused branch is kept for safety but no session reaches it), and the motion-write timeout ("the machine did not acknowledge a write within 10 s; whether it arrived is unknown"). Unchanged and without a stop: `MEDIA_CHANGED` and `MEDIA_CHANGED_PROGRAM` between steps, `UNITS_UNCONFIRMED`, the tool refusals and every refusal before the header. Each refusal is logged (`<name>: '<title>' refused before its first write: ...`).
- **Multi-write steps** (long cut paths):
  1. Before the first write: wait until ready ('0'). If the step contains D or TF, re-check the tools.
  2. Write the chunks in **batches of at most 1024 bytes** (the profile's `batch_bytes`; 1024 on every model today). After each batch, wait until ready, so that when a stop comes at most one batch has been sent and not yet run. From the firmware analysis ESC 09 drops it; that has not been seen on a machine (docs/PROTOCOL.md 8 and 9). `MotionSession.batch_open` is true from a batch's first write until the ready read after it: a pause in that time is a pause in the middle of a batch.
  3. Check the stop flag between every chunk, in every wait, and before the step reports ok. While the machine is paused, wait (no chunk is written).
  4. Every chunk goes through `write_validated`, with the plan's validator bound to the job.
- **Tool rule.** The plan supplies `required_tools: dict[holder:int, code:int]`. Every write containing `D` or `TF` (the profile's `lowering_prefixes`) re-reads ESC 15 and requires each used holder to report its code, read with the profile's grammar and reply slots (`MachineProfile.holder_codes`; a reply it cannot read is unclear, and the raw reply is shown). Code 0 is accepted only if the spec says `allow_unrecognized_tool` for that holder.

### `opencutter.__main__`
- `opencutter`, or `python -m opencutter` with no arguments, starts the GUI (`opencutter.gui.app:main`).
- Subcommands: `serve [--force] [-v] [--idle-exit SECONDS]`, `status`, `info`, `stop` (the machine stop), `pause`, `resume`, `service stop`, `service status`, `dry-run`, `pen-test`, `cut-test`; and `--version` (version, build and API).
- `pause` and `resume` (`command(client, kind)`): one pause or resume op through a service of this very build, for the session that runs now; they print `Resume sent (ESC 08); the machine now reports 1 = Busy.` (or `Pause sent (ESC 07) ...`, with a note when the machine still or not yet reports Paused), `Not sent: <reason>` on stderr for a refusal, or `!! ... may have reached the machine` for a failed write; exit 1 when nothing was sent.
- A test program's step has no time limit (`run_step`): the service is pinged every `WATCH_EVERY` (2 s) and `watch_lines(ping, seen)` prints the changes (`PAUSED_LINE` or `PAUSED_KEY_LINE`, `GOES_ON_LINE`, `NO_ANSWER_LINE` from 7 s without an answer); `WATCH_MISSES` (3) pings in a row without an answer send the stop (`!! no answer from the service (...): sending STOP...`). `status` adds `Paused (the open job waits for the machine)` while the stop ping says `paused`, or how long the machine has not answered.
- The stop: `opencutter stop` and the Ctrl+C stop of a test program ask for `stop(check=True)` and print, after the unchanged `STOP sent ...` line, `after_stop_line(resp)`: `  the machine now reports status ...`, `!! the machine still reports Busy ... PRESS THE POWER BUTTON ...` or `  the machine still reports Paused 15 s after the stop: press Unload on the machine; ...` on stderr; never a claim that the stop is proven. `motion_words(name)` says what a ping's `motion` is ("a job from the app", or "<name> (a test program)"), for `service stop` ("is running a job from the app"), `service status` (`job:     a job from the app is running`) and `status` (`running: a job from the app (last reported status '0' = Ready)`). A start-up refusal of `serve` writes two dated lines to stderr (`HH:MM:SS the background service did not start, <ISO date>:` and `HH:MM:SS <refusal>`) and exits with 1; `client.last_log_line` still returns the refusal.
- Machines: `--help` ends with `machines_help()`, from the registry: the TESTED firmware lines, the UNTESTED models and lines, and the models it recognizes but does not drive. `status`, `info` and `service status` ask for the ping's machine fields (`with_machine`, `{"op":"ping","machine":true}`): `status` prints `profile: <name> (<id>), <support>` (`SUPPORT_WORDS`: "tested on real hardware", "not yet tested on this model"; a TESTED model on an UNTESTED firmware line is `UNTESTED_FIRMWARE`, "not yet tested with this firmware"), `info` adds `Profile:` and `Test programs:` (`program_names(profile_id)`, or "none for this machine yet"), and `service status` adds the support words and the profile id to the `model:` line of a machine that is not tested (a tested CAMEO 4 prints exactly the lines from before profiles), and `refused: <reason>` for a recognized model. The status and tool words come from the machine's profile (`ping_profile(ping)`). `dry-run`, `pen-test` and `cut-test` refuse a model without test programs before any prompt (`NO_PROGRAMS`).

### The background service
The daemon (the "background service" in the app's words) outlives the window: the app starts it detached and it keeps the machine's only Bluetooth link. These rules keep one service per user, make it identifiable and stoppable, and let it go when nobody uses it.

- **One runtime directory.** `protocol.runtime_dir()` is `$XDG_RUNTIME_DIR/app/<id>`, where `<id>` is `$FLATPAK_ID` inside a Flatpak sandbox (`/.flatpak-info` exists, `protocol.FLATPAK_INFO`) when it is a valid application id, else `opencutter.APP_ID`. The instances of one Flatpak app share their `$XDG_RUNTIME_DIR` (Flatpak ≥ 1.11), but it is not the host's: only `$XDG_RUNTIME_DIR/app/$FLATPAK_ID` is the host's same path. So this one directory is the same for every instance of the app, its command line (`flatpak run --command=opencutter …`) and an installation outside Flatpak: they all find the same service. A `$FLATPAK_ID` outside a sandbox (leaked into a host command's environment) is ignored, so it never splits the service. It is None without `$XDG_RUNTIME_DIR` (never /tmp). The socket `opencutter.sock` and the lock `opencutter.lock` live there.
- **Validation.** The daemon creates the directory (and `$XDG_RUNTIME_DIR/app`) with mode 0700 when missing, then checks it with `lstat`: a real directory (not a symbolic link), owned by this user, with no group or other permission bits. Otherwise it refuses to start with a plain line; it never changes or removes an existing path. Only the last component is checked: inside a Flatpak sandbox, `$XDG_RUNTIME_DIR/app` may be set up by Flatpak itself. Clients only connect; they never create it.
- **Locks.** The daemon holds three flocks for its lifetime: its own `opencutter.lock`; `$XDG_RUNTIME_DIR/opencutter.lock`, where builds before 0.1.0 locked (while such a daemon runs, a new one refuses with "an older OpenCutter background service is running; stop it with `opencutter service stop`", which the app shows as `machine.OLDER_SERVICE`); and the legacy prototype daemon's `cameo4.lock`. No two daemons of any generation run together. One limit: the two old locks lie directly in `$XDG_RUNTIME_DIR`, which a Flatpak sandbox does not share with the host, so a daemon inside the Flatpak cannot see a host daemon of a build before 0.1.0 (and the Flatpak app cannot replace it). Only the BlueZ "held elsewhere" check keeps them apart. Builds before 0.1.0 were never released; whoever still runs one stops it before the first Flatpak run, with `opencutter service stop` on the host (or by starting the 0.1.0 host app once, which replaces it).
- **Identity.** `opencutter.identity`: `__version__`, `BUILD` (a 12-hex-digit hash of the version and the package's `.py` sources as they are on disk when the process starts: their sorted relative paths and bytes, computed once at import; it catches a code change without a version bump; an installation without sources hashes its `.pyc` files, and where there are no files at all the version still tells releases apart), `build_on_disk()` (the same hash of the files as they are now) and `API_VERSION`, the version of this client/daemon contract, **2** (1 until 0.1.0). Raise `API_VERSION` when an older client must not use a newer service or the other way round. The ping reports all three and the `pid`; the daemon imports the job package when it starts, so one process runs one build. `RUN_ID` is a random id of this process (16 hex digits): the app starts the service with it in `$OPENCUTTER_STARTED_BY` (`STARTED_BY_ENV`), and the service reports it as `started_by` (`identity.started_by()`, None when unset or not a run id), so that the app knows the service it started itself without relying on pids (`DaemonClient.started_here`).
- **Shutdown op.** Refused while a session is open or opening. Otherwise it answers `{"ok":true}` and the daemon ends through the same path as SIGTERM: the stop sequence only if a step is still running (never the case here), then the Bluetooth link is released (`Cameo4.disconnect()`: BlueZ drops the link at once; nothing is written to the machine), then the socket is removed and the locks are released, in that order. `client.shutdown_service(path)` sends it and waits (at most 10 s) until that process has ended (its pid from `SO_PEERCRED`).
- **Idle exit.** `serve --idle-exit SECONDS` (0 or absent: never; a hand-started `opencutter serve` keeps running). The app starts the service with `--idle-exit 900`. When no client request of any kind (a ping included) arrived for that long and no session is open, the daemon logs one line and ends like the shutdown op. The app pings every 2 s, so this happens 15 minutes after the app was closed; the machine is then free for other programs.
- **Replacing a service of another build (the app).** `MachineMonitor` compares every ping with `identity.same_build`. A service of another build or API, or one without a build (an older one), or an older one answering only on `$XDG_RUNTIME_DIR/opencutter.sock`:
  - runs a job (`motion` not null): it is not touched. Send and Test Cut are blocked with `machine.OTHER_VERSION_BUSY` (`MachineState.blocker`) and the next poll looks again;
  - otherwise it is replaced, at most **once per run** (Try again or Connect allows one more): a service with a build gets the shutdown op; an older one without it gets SIGTERM through `client.terminate_older_daemon`, which sends it only when the pid comes from `SO_PEERCRED` on that very socket, the peer's uid is ours, `/proc/<pid>/cmdline` is Python running OpenCutter's `serve`, and a ping on that same connection, right before the signal, says no session runs. The wait for the old process to end is bounded (10 s) and never blocks the GTK main loop; then the app starts its own service (`--idle-exit 900`) and connects as usual. Meanwhile the state is Connecting with the line `machine.UPDATING_SERVICE`;
  - when the app itself is the old side (OpenCutter was updated or edited while it was open: `identity.build_on_disk()` is no longer `BUILD`, or the service the app started itself, `DaemonClient.spawned_pid`, reports another build), it replaces nothing (every service it starts would be of the other build): Could not Connect with `machine.APP_OUTDATED`, "Close it and open it again";
  - when this run's replace failed, the old service is the app's own, not another copy: `machine.SERVICE_NOT_REPLACED` when it was asked to end but did not within 10 s ("wait a moment, then press Try again"), `machine.SERVICE_NOT_STOPPED` when the guarded SIGTERM refused ("restart the computer"); Try again tries once more;
  - when a service of another build shows up again after a replace (for example a Flatpak and a pip copy of different versions), the app does not fight: Could not Connect with `machine.another_version(name)` (`ANOTHER_VERSION` for the CAMEO 4; the name is the layout's machine);
  - the app never sends a job or a Test Cut to a service of another build: the Send blockers, a ping in `JobRunner` right before the session (`machine.OTHER_VERSION_REFUSED`), and the service's own check of the session request's `build` and `api`.
  A service whose ping says `stopping` counts as gone: it is neither a dropped link nor replaced, and `DaemonClient.ensure_daemon` (the app's start, Connect, Try again) waits for it to end (at most `client.ENDING_WAIT` = 25 s, without blocking the main loop) before it starts a new one (`machine.SERVICE_ENDING` when it does not end). A service on `$OPENCUTTER_SOCKET` is never replaced. Whether the machine accepts the new service's connection without a power cycle is likely (seen once after a clean release) but not verified; if not, the usual `unreachable` reason and banner apply.
- **Disconnect.** The connection popover has Disconnect while connected (insensitive during a job, here or elsewhere): it sends the shutdown op, so the machine is free for other programs at once, and the state becomes Not Connected with `machine.released(name)` (`RELEASED` for the CAMEO 4; `MachineState.released` is set, so views need not compare the text), naming the machine it released. While it waits for the service to end, the polls (and Connect) leave the state alone and nothing may be sent (`MachineState.blocker` = `machine.disconnecting(name)`). A refusal is a toast in plain words (`machine.not_disconnected_busy(name)`, `NOT_DISCONNECTED`); the service's own error goes to the app's log. Nothing starts again by itself until Connect (or Try again).
- **Command line.** `opencutter stop` is the machine stop (ESC 09 twice) and reaches every daemon: the service socket, `$XDG_RUNTIME_DIR/app/<APP_ID>/opencutter.sock` whatever the environment says (`client.app_socket_path()`), `$OPENCUTTER_SOCKET`, `$XDG_RUNTIME_DIR/opencutter.sock` of builds before 0.1.0 and `cameo4.sock` of the legacy prototype daemon (`__main__.stop_targets()`; all but the service socket and `$OPENCUTTER_SOCKET` are reported only when a daemon answers). `opencutter service stop` ends the service on the service socket (and `$OPENCUTTER_SOCKET`) with the shutdown op and an older one with the guarded SIGTERM; it never writes to the machine, refuses while a job runs (cancel it in the app or with `opencutter stop`), prints one line per service and exits 1 if one still runs. `opencutter service status` shows version, build, API, pid (from `SO_PEERCRED`), socket, machine and job, or "not running" (exit 1). The motion commands (`dry-run`, `cut-test`, `pen-test`) refuse to run on a service of another build and say to run `opencutter service stop` first.
- **Log.** Each start of the service, once it has its directory and its locks, writes `OpenCutter <version> (build <b>) background service started, pid <n>, <ISO date>` (a daemon that refused before that writes only its refusal, as two dated lines). `daemon.log` is appended to, so it holds one such line per start. When the app starts a service and `daemon.log` is larger than 1 MiB, it is renamed to `daemon.log.1` first (same opener rules: no symbolic link, regular files only). A `--- YYYY-MM-DD ---` line starts each new day. Without `-v` the log has:
  - status changes, only on a real change and only once the link passed the gate: `[status change] X = term`, with ` (ESC 05)` when an ESC 05 reply showed it; Ready and Busy changes only while a session is open, for `STOP_WATCH` (30 s) after any stop, or with `-v`. `-v` also logs every write and reply;
  - every stop as one of `STOP (ESC 09 x2) sent, pair N on this link`, `STOP (ESC 09 x2) FAILED, pair N on this link: write 1 acknowledged after 0.03 s; write 2 no Write Response within 2 s`, `joined the STOP in flight (pair N on this link): sent|FAILED`, `STOP already sent (pair N on this link); not sent again`; `after the stop the machine reports X = term` (or `still reports 3 = Paused N s later: press Unload ...`, or `the status could not be read (<why>)`) for a stop with `check`; `daemon stopping between steps of a session (the machine may be idle) -> STOP`;
  - the pause: `job: the machine paused (3) during '<step>', batch b/n; waiting: nothing more is sent until it goes on`, `job: the machine goes on (1) after N s`, `job: the machine left Pause without going on (3 -> 0, no 1 and no Cancelling seen): ended`, `job: resume asked: ESC 08 sent (the machine read 3)` (and `pause asked: ESC 07 ...`), `job: cancel while paused: the machine read 3 for 5.3 s, then 4, then 0`;
  - patience: `job: ESC 05 not answered for 7 s (write acknowledged after 0.04 s; 3 status indications since, last '1' 1.2 s ago); asking again, nothing new is sent`, `job: ESC 05 write not acknowledged after 5 s (Write Response missing; ...); waiting for it`, `job: ESC 05 answered again after 11.4 s (2 queries, 1 late reply dropped)`, `slow Write Response: 1b 05 after 2.6 s`; the first failure of a one-shot op (`the info op failed: ...`) and its recovery;
  - the owed stop: `a stop is owed to NAME [addr] (...)`, then `link back: sending the stop owed from the lost session: sent|FAILED`;
  - the links: `Bluetooth link to NAME [addr] is up; reading its FG reply` after every open, `the FG check on NAME [addr] did not pass: ...` for every gate failure, `connected to ...` once a link passed the gate, `waiting for Bluetooth (it is off, or there is no adapter)` and every 10 minutes `still waiting for ... (N tries since HH:MM; last: ...)`;
  - the refusals: `<name>: refused at open: ...` and `<name>: '<title>' refused before its first write: ...`.
- **Inside Flatpak.** The app, and every `flatpak run` of it, runs in a sandbox of its own (`protocol.in_flatpak()`), with its own PID namespace. The rules above hold there too, with these differences:
  - *How the service starts.* `client.service_command()` starts it through the Flatpak portal: `flatpak-spawn --env=OPENCUTTER_STARTED_BY=<run id> --directory=/ opencutter serve --idle-exit 900`, with stdin from `/dev/null` and stdout and stderr in `daemon.log`, opened by the window (flatpak-spawn passes all three on to the service). The portal runs it in a new sandbox of the same app with the same permissions (no `--host`), not tied to the window (no `--watch-bus`), and from the same commit as the window (no `--latest-version`). A plain child of the window would not end the moment the window does (measured with Flatpak 1.16.6: the sandbox's init keeps it running), but it would keep the window's sandbox running, and it would end with that sandbox whenever the sandbox is torn down (`flatpak kill`, which sends SIGKILL; a launcher's `--die-with-parent`): without a stop and without the clean link release.
  - *The helper.* flatpak-spawn itself waits for the service and exits with its status, and while it waits it keeps the window's sandbox running. So `DaemonClient.ensure_daemon` ends it once the service answers, with SIGKILL (`client._end_spawn_helper`): flatpak-spawn passes SIGTERM, SIGINT and SIGHUP on to the service, which would then end; without `--watch-bus` the portal keeps the service running when the helper goes. When flatpak-spawn exits before the service answers, that is a failed start as on the host: `spawn_error` is the last line of `daemon.log` (the service's refusal, or the portal's or Flatpak's own error). A status 0 before an answer is not a failed start: the wait goes on until the timeout. A helper that still waits when the window closes or the app quits is ended the same way (`DaemonClient.end_helper`: `MainWindow`'s close, `OpenCutterApp.do_shutdown`, and a cancelled `ensure_daemon`), so the window's sandbox never outlives the app; the service it asked for starts and runs on by itself.
  - *Updates.* Flatpak keeps an updated version that is still in use (in `.removed/`) until its last sandbox has ended, and the portal starts the caller's own commit, also from there. So the window and the service it starts are one build, also after an update while the window is open (measured with Flatpak 1.16.6 in a private installation: after a bundle update, flatpak-spawn from the open window started the old commit from `.removed/`; with `--latest-version` it would have started the new one). After the old window was closed, the new window replaces the idle old service once, as any service of another build. Should the window's commit be gone all the same, `flatpak run` fails with `error: app/<id>/<arch>/<branch> (commit <c>) not installed` in `daemon.log`, and the app shows `machine.APP_OUTDATED` ("Close it and open it again"); nothing starts by itself until Try again, so there is no loop. `identity.build_on_disk()` never changes inside a sandbox (its /app does not change), so in the Flatpak only `started_here` with another build could tell that the app is the old side.
  - *Pids.* The ping's `pid` is in the service's own sandbox (normally 2). From another sandbox (the window, a `flatpak run --command=opencutter …`) `SO_PEERCRED` gives pid 0, because that process is not visible there: `shutdown_service` then waits (at most 10 s) until the service has removed its socket, which it does after it released the link (Disconnect, `service stop` and the replace work the same way); `terminate_older_daemon` refuses (it is only for a service of a build before 0.1.0, whose old socket a sandbox cannot see anyway); `opencutter service status` prints "not visible from here" instead of a pid. From the host, `SO_PEERCRED` gives the service's host pid. The app knows the service it started itself by its run id (`DaemonClient.started_here`: a service that reports another run's id is not its own, whatever its pid; without a run id, the pid tells, and only outside a sandbox, where `spawned_pid` is set).
  - *The command line.* Every instance of the app shares `$XDG_RUNTIME_DIR/app/<id>`, so `flatpak run --command=opencutter io.github.mortyniners.OpenCutter service status`, `service stop` and `stop` from another instance reach the service as on the host.
  - *Host and Flatpak together.* A host installation (pip or pipx, 0.1.0 or later) and the Flatpak use the same directory: Flatpak shares exactly `$XDG_RUNTIME_DIR/app/<id>` with the host. They see each other's lock and socket, so only one service runs, and each app replaces an idle service of the other's build once per run (then `machine.ANOTHER_VERSION`). That is accepted; whoever has both closes one of them. Their logs differ: `$XDG_STATE_HOME` is `~/.var/app/<id>/.local/state` in the Flatpak, so `daemon.log` is there, and `machine.log_hint()` names it. The system bus proxy of the service's sandbox writes to the same `daemon.log` (its warnings appear there when it cannot reach the system bus).
  - *Background Apps.* Once the window is closed, the service's sandbox is an instance of the app without a window, and GNOME lists the app under Background Apps (quick settings). Its close button there first asks the app's D-Bus name for the `quit` action; nobody owns that name once the window is closed (the app is not D-Bus activatable), so GNOME runs `flatpak kill`, which ends the service with SIGKILL: no link release, and the machine may need a power cycle. The same happens when the user turns off the app's background permission (Settings → Apps → Run in Background): xdg-desktop-portal kills windowless instances. The service cannot prevent either; it describes itself instead: `device.portal.announce_background` sets the Background portal's status line (`SetStatus`, `portal.BACKGROUND_STATUS`, at most 96 characters: "Holds the CAMEO 4 link. Use Disconnect in OpenCutter to release it; do not close it here."), which GNOME shows under the app's name. It talks to the session bus only, keeps that connection until the service ends, and is best effort (one log line when there is no session bus or the portal has no `SetStatus`). The README warns about both controls. Answering `quit` on the app's name (the service owning it while no window does) would make the close button a clean shutdown, but needs the GUI to take the name over (`G_APPLICATION_REPLACE`); not done.
  - *Session end.* At a logout systemd stops every app sandbox's scope (GNOME: `app-flatpak-*.scope`, 5 s) with SIGTERM to all its processes. The service's SIGTERM path (the stop sequence during a step, then the link release) reaches BlueZ through the sandbox's D-Bus proxy, which handles no SIGTERM and ends at once; that it is in the same scope is read from Flatpak's code, not measured. So at session end the stop may not get through in the Flatpak (a host installation talks to the system bus directly). Therefore, while a job or Test Cut runs, the window asks the desktop not to log out or suspend (`Gtk.Application.inhibit`, LOGOUT and SUSPEND; in the Flatpak GTK asks through the Inhibit portal on Wayland and X11, while GTK's Broadway backend has no inhibit at all), see "Safety in the GUI".
  - *No Bluetooth.* Without the `org.bluez` permission (removed with `flatpak override`) or with BlueZ not running, the service's look at BlueZ fails: the ping's reason is `no-bluetooth`, and the app shows Could not Connect with `machine.NO_BLUETOOTH` at once.

### The machine model gate
OpenCutter has been tested on one machine only: a CAMEO 4 whose `FG` reply is `CAMEO 4 V5.05` (padded with spaces). The other Silhouette cutters offer the same Bluetooth service and would pass discovery, but their mats, force ranges, tool holders and commands differ. So the daemon checks the model on every link before it uses it, and drives only a model and firmware line that has a machine profile (TESTED or UNTESTED, see "Machine profiles"), with that profile. The check is an allowlist and fails closed.
- **Where.** In `daemon.serve`, on every new link: at the first connect, and again after every link loss and reconnect. `--force` does not skip it (it only lets the daemon join a link held elsewhere).
- **What is sent.** After `Cameo4.open()`, the usual ESC 05; then, under the query lock, `FG` (the link allows only ESC 05 and `FG` before the gate). `machines.detect(fg)` decides (docs/PROTOCOL.md 3.4). Only the verdict USE opens the gate: the daemon sets `Cameo4.profile` to `Detection.profile`, still under the lock, and where the profile says that `FG` claims the session (`fg_claims_session`: on a CAMEO 4 status 1 Busy becomes 2 Load Media; every profile today) it reads ESC 05 once more, so the first status clients see is right. That status read is not part of the check: when it does not answer in time, the link is used all the same (`FG` answered in time, so the link drops the late reply by count, and the status indications set the status), because the tested CAMEO 4 accepts a new link only after a power cycle. Only then is the link usable: `Cameo4.machine` is set to `model_text(fg)` and `state["c"]` to the link, and the log says `connected to <name> [<address>], <model>, status ...`, with ` (untested)` after the model for a machine that is not tested (the CAMEO 4 line is unchanged). Everything that writes to the machine (sessions, `esc`, `query`, `info`, `stop`) checks both, and from then on uses the link's profile.
- **Another model.** Anything else gets nothing more: no ESC 09, no other query, no motion. That is a RECOGNIZED model (`CAMEO 3 V1.60` and four spaces, or a CAMEO 4 on an unknown firmware line such as `CAMEO 4 V9.05`), an UNKNOWN one (`CAMEO 5 PRO V1.07`; `CAMEO 4 PLUS V5.05` or `CAMEO 4 V1.20` without the firmware's four spaces), or none (an empty reply). The ping says `wrong-model` and the `model` (`protocol.reported_model`: null for an empty reply, and the refusal then says that the machine did not report its model), and for a recognized model its machine fields name it with its reason ("Socket protocol"). One log line names the machine and its model, with the recognized model's reason, and the link is released (`Cameo4.disconnect()`: nothing is written). The refused machine's model is kept apart from the accepted one's: when the reason falls back to `wrong-model` after a CAMEO 4 was used and went away, the ping and the refusals still name the refused machine. The machine's address is kept for the life of the service, and `find_bonded_cameo(skip=...)` skips it, so another paired CAMEO is tried; while no other is found, the reason stays `wrong-model`. With `serve --address` naming a refused machine there is nothing else to try: the service waits (`WRONG_MODEL_WAIT`, 60 s at a time, no looks at BlueZ) and keeps saying `wrong-model`; the shutdown op, the idle exit and signals end it as usual. A new service (after `opencutter service stop`, the idle exit or a restart of the computer) looks at every paired machine again.
- **No answer.** When `FG` fails or times out, the link is not used: the reason is `unreachable` and the daemon tries again later, as for a failed connect (another paired machine first, see "Several paired machines"). Replies carry no id, so the late answer of a query that timed out could be taken as the answer of a later one (`Cameo4` drops late replies by count, but resyncs after two timeouts in a row). So that link is released and the next try starts on a new link with a reply stream of its own; the late `FG` reply never reaches a query of a link that is used. For the same reason an `FG` answered by a status digit (`protocol.is_status`: the late answer of an earlier ESC 05 on that link) is not a model: it is a failed probe in the same way, never a refusal (which would last as long as the service) and never an acceptance. A machine that accepts a connection only after power-up then needs to be switched off and on (the `unreachable` text says so). The ESC 05 after a passing `FG` is only a status read (see "What is sent"): only an error other than a timeout costs the link.
- **Several paired machines.** Discovery tries the paired machines in turn: a machine whose connect or `FG` failed in this round is skipped at the next look while another paired one has not been tried (`find_bonded_cameo(skip=...)` with the refused and the tried addresses); when every one was tried, the next round starts with all of them. So a machine that is switched off, or one that does not answer `FG`, cannot hide one OpenCutter drives listed after it. With one paired machine nothing changes: it is tried again every `RETRY_WAIT` (3 s). Nothing is sent to a machine for this but ESC 05 and `FG` on a new link.
- **The stop when the service ends.** A signal while motion is possible (a step runs, or `MotionSession.motion_possible`: between steps it logs `daemon stopping between steps of a session (the machine may be idle) -> STOP`) sends the stop sequence, not forced, only through a link that passed the gate (`_usable`) to the session's own address. After a link loss the loop may already hold a new link whose gate is under way (maybe to another model): that link gets nothing.
- **The owed stop on a new link.** When a stop is owed to a machine (see the daemon's protections above) and a new link to that same address passed the gate, the stop goes out once on it, after the gate and before `state["c"]` is set, with the log line `link back: sending the stop owed from the lost session: sent` (or `FAILED: ...`, kept for the next link). Before the gate nothing but ESC 05 and `FG` is sent, not even this stop; a machine owed a stop gets `FG_TIMEOUT_OWED` (10 s) for its `FG` reply, since a machine still busy may answer late. A machine that answers even later is dropped by the gate: then only its power button stops it.
- **Paired only.** `find_bonded_cameo` returns only a device that BlueZ reports `Paired` (or `Bonded`): without `--address`, the first paired device whose name starts with one of the registry's Bluetooth name prefixes (`CAMEO`, `Portrait`, `CURIO`, any case) and that offers the vendor service; with `--address`, that device without the name and service checks, and a known but unpaired one gives "pair it first" (`not-paired`).
- **Command line.** `opencutter status` and `service status` print the model (`model:`), `info` the `FG` reply; `status` and `info` also the profile and its support level (see `opencutter.__main__`). For a refused machine `status`, `info` and the motion commands print the refusal (for a recognized model its reason and "Nothing more is sent to it.", else `wrong_model_message`) and exit with 1, and `service status` prints `machine: not connected (wrong-model)` and `model: <model>, refused: ...` (the recognized model's reason, or that OpenCutter cannot drive this model; `not reported, refused: ...` for a machine that named no model).
- **The app.** `MachineMonitor` maps the reason `wrong-model` to `MachineState.wrong_model` with the ping's `model` (`MachineState.model`, through `machine.shown_model`) and the problem `machine.WRONG_MODEL` ("This machine reports itself as “{model}”. OpenCutter cannot drive it and will not send jobs to it."), at once (`FAIL_AT_ONCE`, no grace time). Without a model it is `machine.WRONG_MODEL_UNKNOWN` ("This machine did not report its model. ..."). Neither text names the layout's machine or says anything about testing. For a model OpenCutter recognizes, the machine ping's fields (`support` "recognized", `refused_reason`, `MachineState.recognized`) give its name and plain reason instead where the problem is shown (`connection.shown_problem`, through `machine.other_machine_hint`: the ping's `refused_reason`, else the registry's `RecognizedModel.message`): "OpenCutter recognizes this CAMEO 3 but cannot drive it yet: there is no known way to stop it from the computer, ...". The link is `FAILED`, but every view says "Unsupported Machine" (`machine.UNSUPPORTED`) instead of "Could not Connect": the pill (red), the status bar (its tooltip gives the problem), the banner and the connection popover's alert (`connection.failure_title`); the popover's device row shows the reported model with "Not Supported" ("Unknown machine" without one), and Preferences' Model row "Recognized, not supported yet" or "Not supported". The pill never calls the refused machine by the layout's machine's name: it shows the state without a name, and its tooltip names the reported model (`connection.refused_name`). Nothing offers Try again (the banner has no button, the popover and the first run's Connect page no Try again or Connect): the service never uses that machine again while it runs, and it connects by itself to a paired machine it drives once that one is switched on. So the popover and the first run's Connect page drop the pairing and switch-off-and-on tips (and "the machine moves only after you press Send") and say that instead (`machine.OTHER_MACHINE_HINT`, built from the registry by `drivable_hint()`: every model OpenCutter drives (`drivable_models()`), with no word about which of them were tested, and how to use one; it names the CAMEO 4's firmware lines, "CAMEO 4 (firmware V1.xx or V5.xx)", since a CAMEO 4 of another firmware line is refused as well). Page Setup and the Tool cards say "Not detected" (without "yet"). Send and Test Cut stay disabled with `sending.NOT_SUPPORTED` ("This machine is not supported."), before the material and design checks, since nothing on screen can change it. When connected, the popover's Firmware row shows the accepted machine's `model` (else `info`'s `firmware`). The model is the machine's own text: the app shows it only as plain text or escaped (`failure_markup`).

## job, pure Python, no I/O

Every job function takes the active `MachineProfile` (`profile=CAMEO4` by default) or reads it from `JobSpec.machine`; the package imports only `opencutter.machines` from outside itself. The ranges in the comments below are the CAMEO 4's; other models: their profile's `Ranges` (docs/PROTOCOL.md 11).

### `opencutter.job.spec`
```python
@dataclass
class ToolSettings:          # one condition block (docs/PROTOCOL.md 5)
    holder: int              # Holder.number: 1 (left) or 2 (right); 1 on a one-holder model
    tool_code: int           # ESC 15 code required in that holder (2 AutoBlade, 4 Kraft, 7 Sketch Pen, ...)
    speed: int               # ! 1..30
    force: int               # FX 1..33
    acceleration: int        # TJ 1..10 (a whole number; not sent to a model without TJ)
    offset: int              # FC 0..99 (blade offset; 0 for pens)
    line_segment_overcut: bool   # FE
    overcut: tuple[int, int] # FF start,end 0..9
    blade_depth: int | None  # TF 0..10, only a tool that takes a depth (the AutoBlade in holder 1); None otherwise
    passes: int = 1          # 1..10 (path repeated)
@dataclass
class CutGroup:
    settings: ToolSettings
    paths: list[list[tuple[float, float]]]   # polylines in DOCUMENT mm: x right, y down, from the mat origin
@dataclass
class JobSpec:
    mat: str                                 # Mat.key of the machine's profile: "12x12" on the CAMEO 4
    media: tuple[float, float, float, float] # x, y, w, h in document mm on the mat
    groups: list[CutGroup]
    preview_outline: bool = True             # tool-up trace of the bbox before cutting
    allow_unrecognized_tool: dict[int, bool] = field(default_factory=dict)
    machine: str = DEFAULT_MACHINE           # the profile id the job is made for ("cameo4"); last field
    def to_dict(self) -> dict; @staticmethod def from_dict(d: dict) -> "JobSpec"   # JSON-safe, strict types
```

### `opencutter.job.builder`
- `su(mm)`, `doc_to_cutter(x_mm, y_mm) -> (a, b)`. `a` = su(y) is the feed and `b` = su(x) is the carriage (docs/PROTOCOL.md 4).
- `header(mat, profile)`, `condition_block(ToolSettings, profile)`, `path(contours_su, passes)`, `trailer(profile)`, `chunk(cmds, limit) -> list[bytes]` (callers pass `profile.max_write`). The texts come from the profile (`mat_texts`, `area_texts`, `condition_texts`, `trailer_texts`): the per-holder forms on a two-holder model, the plain forms without `J` on a one-holder model, no `TJ` where the model has none, and `TG9 FN0 TB50,0 FM1` for an expand mat.
- `test_cut_contours(x_mm, y_mm) -> list[list[(x,y)]]`: a 10 mm square with a triangle inside, as in Studio's Test Cut, in document mm.
- `MATS = {"12x12": {"tg": 1, "area_su": (30, 30, 6066, 6066)}}`: the CAMEO 4's, computed from its profile; other models: `profile.mats`.

### `opencutter.job.validate`
- `class UnsafeJob(ValueError)`.
- `job_profile(spec, profile=None) -> MachineProfile`: the profile the job is checked and built with. Without `profile`, `registry.by_id(spec.machine)`; with one (the daemon's: the machine on the link), its id must be `spec.machine` ("this job was made for the X, but the machine is the Y"). An unknown id, a recognized model (its plain-words message) and anything that is not a `MachineProfile` are refused; a profile that is not the registry's own entry must pass `machines.safety.check_profile`. `job_mat(spec, profile)`: the mat must be one of the profile's and offered at its level (`Mat.offered`). `bind_job(spec, profile=None) -> BoundJob(validator, profile, mat, media_box)`.
- `validate_spec(spec, profile=None) -> None`. It checks, with the profile:
  - every range listed in `ToolSettings` (`profile.ranges`);
  - the mat is known and offered;
  - the media rect lies within the mat;
  - **every point** lies within the media rect (0.5 mm tolerance) **and** within the mat cut area;
  - point count ≤ 500 000 and passes ≤ 10;
  - the holder is one of the profile's;
  - `blade_depth` is set only for a tool that takes one (`Tool.depth`: the AutoBlade in holder 1);
  - tool_code is valid for the holder and usable (`Tool.usable`); Rotary Blade (5) and Punch Tool (6) are refused;
  - tools that are not blades (Sketch Pen, Foil Tool; `Tool.blade`) have offset 0, no Line Segment Overcut and overcut (0, 0).
- `make_write_validator(spec, profile=None) -> Callable[[bytes], None]`. It returns the byte-level validator that the daemon applies to every write:
  - only the exact header, condition-block and trailer commands the builder emitted for this spec (on the CAMEO 4: `TG1`, `FN0`, `TB50,0`, `\a,b`, `Za,b`, `J1`/`J2`, `!s,n`, `FXf,n`, `TJa`, `FCo,1,n`, `FE0|1,n`, `FFs,e,n`, `TFd,1`), which must also fit the profile's command grammar (`setting_grammar()`), plus `Ma,b` and `Da,b`;
  - ranges;
  - every M/D within the spec's media plus the cut area, with at most as many digits as the profile's `max_coordinate_su`;
  - no D directly after any command other than an M or D inside that box, within the write;
  - no ESC; ETX-terminated; length ≤ the profile's `max_write` (182);
  - never anything from the never-send list (docs/PROTOCOL.md 6), and `machines.safety.check_write` for the profile as a floor under every write.
- `check_plan_sequence(plan) -> None`: the whole-plan check, run once before anything is sent. Every D of every write step must directly follow an M or D inside `plan.media_box`, in the same step.

### `opencutter.job.plan`
- `build_plan(spec, profile=None) -> Plan`. It calls `validate_spec` and builds the steps (docs/PROTOCOL.md 7):
  1. header;
  2. U unit check;
  3. per group, the setup (condition block, with TF last);
  4. if `preview_outline`, a tool-up M trace around the bbox, then the first cut step is marked `confirm=True`;
  5. the cut steps (multi-write; one step per group);
  6. the trailer.
- `Plan(steps: list[PlanStep], required_tools: dict[int,int], validator, summary: dict, media_box: tuple[int,int,int,int], profile_id, units_expected, units_enforced, batch_bytes, slowest_su_per_s, max_coordinate_su)`. `build_plan` runs `check_plan_sequence` on the finished plan. From the profile and the mat: `profile_id` (the daemon checks it), `units_expected` (the mat's expected `U` pair, or None) and `units_enforced` (True for a KNOWN or INFERRED `U`; False for an UNKNOWN one, which only UNTESTED profiles offer), and the pacing limits. The defaults are the CAMEO 4's, except that the unit check defaults to one that cannot pass (nothing expected, but enforced).
- `PlanStep(kind: "write"|"units", writes: list[bytes], title: str, expect: str, confirm: bool=False)`.
- `summary` holds: total path length (mm), estimated seconds (path length / speed, plus the overheads), bbox, the groups (holder, tool name, settings) and the passes.

## presets

### `opencutter.presets.model`
```python
@dataclass
class Preset:               # one material + action + holder row
    material: str; material_type: str; action: str      # Studio terms: "Cut", "Score", "Sketch", "Kraft Cut", ...
    holder: int; tool: str; tool_code: int
    speed: int; force: int; acceleration: int; offset: int
    line_segment_overcut: bool; overcut: tuple[int, int]; blade_depth: int | None; passes: int
    verified: bool = False; machines: tuple[str, ...] = ("cameo4",)   # profile ids the row is for
    def to_tool_settings(self) -> "opencutter.job.spec.ToolSettings"
class PresetStore:
    @staticmethod def load() -> "PresetStore"     # the presets file at $XDG_DATA_HOME/opencutter/presets.json, else BASIC set
    source: dict          # {"kind": "basic"|"file", "description": str}
    def for_profile(self, profile) -> "PresetStore"   # the rows one machine may use (a MachineProfile, a RecognizedModel or an id)
    def materials(self) -> list[str]; def material_types(self) -> list[str]
    def presets_for(self, material: str) -> list[Preset]
    def search(self, text: str) -> list[str]
BASIC_PRESETS: list[Preset]   # small built-in set (the CAMEO 4's); values come from the contributors' own test cuts (CONTRIBUTING.md)
BASIC_PRESETS_BY_PROFILE: dict[str, list[Preset]]   # the Basic set of the CAMEO 4 family: cameo4, cameo4_plus, cameo4_pro
```

**The presets file.** `presets_path()` is `$XDG_DATA_HOME/opencutter/presets.json` (default `~/.local/share/opencutter/presets.json`; a relative `XDG_DATA_HOME` is ignored). The app only reads it, once at startup; people write it by hand or with their own tools. README.md ("Material presets") documents the format for users:
- a JSON object `{"format": "opencutter-presets", "schema": 1 or 2, "description": <optional short text>, "presets": [<Preset.to_dict()>, ...]}` (`FILE_SCHEMAS`, `FILE_SCHEMA = 2` the newest; the schema must be a real int);
- schema 1: every row is a CAMEO 4 row, a `machines` key anywhere is an error, and other unknown keys are ignored, as they always were;
- schema 2: a row may name its machines (`"machines": ["cameo4", "cameo5"]`; without the key it is a CAMEO 4 row); any other unknown key, in a row or at the top of the file (`FILE_KEYS`: `format`, `schema`, `description`, `presets`), is an error, so a misspelt `machines` cannot turn another model's row into a CAMEO 4 row. A top-level `machines` is an error in both schemas: machines are named per row;
- each preset has every `Preset` field (`verified` is optional, default false; `machines` is written only for a row that is not the CAMEO 4's alone), with the strict types of `Preset.from_dict` (no bool for int, `overcut` a pair, `blade_depth` an int or null);
- `machine_profiles(p)` resolves the row's ids: an unknown id, a RECOGNIZED one, an empty list or a duplicate is an error. `check_values(p, profile=None)` checks the row against every machine it names, each with its own profile: a tool that machine detects in that holder (code 0 is refused), its ranges (overcut 0..9; acceleration a whole number even without `TJ`), Blade Depth only for a tool that takes one, and Offset 0, no Line Segment Overcut and Overcut 0, 0 for tools that are not blades. Rotary Blade and Punch Tool rows are accepted; the GUI hides them (`gui.sending.is_supported`);
- each (material, action, holder) appears once per machine, and there is at least one preset.

**Which rows a machine gets.** `PresetStore.for_profile(profile)` keeps the store's source and gives the rows that name that machine. The Basic set applies to the CAMEO 4 family only (`BASIC_MACHINES`): a Basic store gives the CAMEO 4 Plus and Pro its CAMEO 4 rows, named for them and not verified (nothing was cut on them), when their profile accepts them; every other model gets no Basic presets and uses Cut Settings or a presets file. A presets file replaces the Basic set for every machine, so with a schema 1 file every model but the CAMEO 4 gets no rows. A build from before machine profiles reads only schema 1 files and treats any other as unreadable, so a schema 2 file never gives it another model's rows.

A missing file gives the Basic set. A file that cannot be read or breaks any rule above also gives the Basic set: the reason is logged as a warning and kept in `source["file_error"]`.

OpenCutter contains no code or data that reads, decrypts or redistributes Silhouette Studio files, firmware or data (CONTRIBUTING.md); a test checks this.

## gui

`opencutter.gui.app:main()` starts the `Adw.Application` with application id `io.github.mortyniners.OpenCutter` (`opencutter.APP_ID`; the data files, the icon names, the AppStream id and the program name (X11 `WM_CLASS`) use the same id, and a test checks that they match). It uses asyncio through `gi.events.GLibEventLoopPolicy` (PyGObject ≥ 3.50), so the GUI awaits `DaemonClient` calls directly.

The UI is English and uses Silhouette Studio's terms (Material, Action, Tool, Blade Depth, Force, Speed, Passes, Test Cut, Send); dark by default, cyan accent. The screens:
- the main window: header bar with Open, document name, machine status pill and Send; the mat canvas; the sidebar tabs Page Setup / Send; the status bar;
- the first run (Welcome, then Connect);
- the connection popover;
- the Load Media sheet and the Send confirmation sheet;
- the job progress view, with a large Cancel Job button that is always visible;
- the finished view;
- error banners, the machine banner (the layout followed another machine: "Use {name}") and toasts;
- Preferences and About.

**Out of scope for now** (do not build them): Action by Line/Fill/Layer, Registration Marks / Print & Cut, Matless, Rotary/Punch actions, the Material Editor, mats a machine profile does not list (the CAMEO 4 has only its 12 × 12 in mat).

**Safety in the GUI:**
- Nothing moves without an explicit click on Send, Test Cut or the outline-confirm "Cut".
- Send and Test Cut stay disabled for a machine the service refused for its model (`sending.NOT_SUPPORTED`, see "The machine model gate"); the service refuses its sessions by itself as well.
- Every JobSpec is made for the layout's machine and mat (`JobSpec.machine`, `JobSpec.mat`). While the detected machine is another profile than the layout's, or the layout followed it and the user has not pressed "Use {name}" yet, Send and Test Cut stay disabled (`LayoutMachine.blocker`); the Send sheet's checklist gets a failing row for it, and the send flow checks again after the Load Media sheet and after the Send sheet (`window.MACHINE_CHANGED`: nothing is sent). The service refuses a job made for another machine than the connected one anyway.
- A note that blocks nothing: the unchecked cut area of a mat whose `U` reply is not known (Page Setup, the Send sheet, the job view). It never disables Send. No note or label says whether a model was tested.
- One send at a time: from the Send or Test Cut click until its job has ended, Send, Test Cut and Open are disabled, and `run_job` never replaces a runner that is still running.
- The job sent is the job on screen: pending length edits are committed first, and the spec is rebuilt and compared with the confirmed one just before it is sent.
- Cancel Job is one click and calls `DaemonClient.stop()`; while the machine is paused, `stop(check=True)`, so that "Stopping…" (with `jobview.CANCELLING_PAUSED`, the pill "Cancelling…") lasts until the machine has ended the job, and the finished page adds `jobview.STILL_PAUSED` when it still read Paused. While a job runs, the sidebar with the big Cancel Job button stays pinned and shown, and the header bar shows a Cancel Job button too; Esc cancels (a window `Gtk.ShortcutController`, BUBBLE and LOCAL, so an open dialog or popover takes Esc first; Escape is no longer in `app.ACCELS`). From Cancel until the stop's reply (`JobRunner.stop_pending`) the finished page reads "Stopping…", and Send, Test Cut, Open, Cut Again and Done wait; `cancel()` returns the same reply to every caller. A failed stop raises a toast that stays, whenever the reply comes, and the red alert above both pages.
- Closing the window during a job asks first, then stops; closing (or Ctrl+Q) right after Cancel waits for that stop's reply. If the stop could not be sent, the window stays open and a blocking alert asks for the power button. When the app ends without asking (a crash, a kill, Ctrl+C in or closing the terminal that started it), only the service's own stop is left: it comes when the client leaves during a step, never between steps (the machine read ready at the end of the step, for example at the outline gate), and nothing comes when the service itself is killed with SIGKILL.
- **Stop Machine** after a run (`win.stop-machine`, no accelerator): a button on the finished page for every outcome (destructive after Cancelled, Failed or Lost, flat after Done) and, after anything but Done, in the header bar (`header_stop`). It calls `client.stop(check=True)`, the stop op without a session (ESC 09 twice and ESC 05 reads, nothing else), is insensitive while not connected (tooltip "Not connected: press the machine's power button."), and says what came back: a toast, `dialogs.still_busy_after_stop` when the machine still reads Busy, `dialogs.stop_not_sent` on failure. When the service keeps reporting Busy for 4 s after a run (the monitor's pings), the finished page says so.
- **The machine's Pause.** While the service says the job waits on a paused machine (the stop ping's `paused`), or the machine's status reads Paused, the pill reads "Paused" (warning tone, no pulse), the status bar "Paused on the machine", the current step shows a pause icon, the progress estimate and the time left stop (elapsed time goes on), and the job view shows `machine.PAUSED_NOTE` when Resume is offered, else `PAUSED_NOTE_KEY`. **Resume** (`MainWindow.resume_job`) is shown only with `paused` and `resume_ok`; **Pause** (`pause_job`) only while a step runs (not at the outline check) on a detected profile with a pause on a TESTED model and firmware line (`MachineState.offers_pause`: the CAMEO 4 on V5), sensitive only with `pause_ok`. Each click sends the service's op once through `JobRunner.resume()` / `pause()` (one at a time, "Resuming…" / "Pausing…" until the answer); nothing is ever sent again by itself: still paused `runner.RESUME_SECONDS` (5 s) after Resume gives `runner.NOT_RESUMED`, a refusal "Resume was not sent: <reason>.", and the paused state shown always comes from the service, never from the click. Both buttons sit above Cancel Job, take no focus on click, and a click within `COMMAND_GUARD_SECONDS` (1 s) of the last answer is ignored, so a double click never lands on the other button. A Cancelling status, or `interrupted` (its digit or `"left-pause"`), shows "Cancelling" or "Stopping…"; the service ends the job with the stop. "Checking connection" (`machine.CHECKING`, warning) and `CHECKING_NOTE` while `no_reply_s` is set (7 s or more without an answer), with `STILL_REPORTS` when status indications came in the last 7 s. No finished page mentions the Pause key; the Load sheet, for a paused machine without a job of ours, says to press Unload or switch the machine off and on ("Do not press Pause to continue."), and never asks to load the mat on a paused machine without Unload first. The info poll after a run keeps the tools read last when `tools` comes back null (a paused or cancelling machine).
- **The load step before every job.** `MainWindow._reload_needed` is set when a run ends after any step went to the machine (every outcome, Done included) and when the link drops from Connected; it is cleared only when the machine reports its load digit, or when the service's `load_seen` count rises past its value at that time. While it is set, Send, Cut Again, Send Again… and Test Cut first show the Load sheet, even when the machine reads Ready, and its Continue waits for the load digit and then Ready. A run refused before its first step (`runner.refused_before_start`, "Nothing was sent") needs no reload.
- **Media and placement.** The Send sheet has a Media row; a Media Size that covers the whole cut area adds a note that blocks nothing (`MEDIA_IS_MAT`). The Load sheet says to put the sheet's top-left corner on the top-left corner of the mat's grid and that Media Size must match the sheet (`sheets.place_text`). A design off the media but inside the cut area gives "Fit to Media" and `sending.OFF_MEDIA` (`geometry.placement_problem`).
- **Link loss and the owed stop.** During a run the pill shows "Connection lost"; at the outline gate Cut is disabled for the rest of the run. The connection-lost dialog follows from the run (Lost, `runner.link_lost`, a drop seen during the run, or no link after it), never for a refusal before the first step, and offers no Reconnect when the link is back already. The monitor reads `PING_STOP_KEYS`: `stop_owed` turning true raises a toast that stays ("A stop could not get through to the {name}. OpenCutter sends it as soon as the {name} is connected again. If it moves, press its power button."), and a rise of `owed_stops_sent` a toast that it was sent. `motion_stopped` from another client at the gate ends the run Cancelled (`runner.stopped_elsewhere()`); the GUI sends nothing for it.
- While a job or Test Cut runs, the window asks the desktop not to log out or suspend (`MainWindow._inhibit_session`: `Gtk.Application.inhibit` with LOGOUT and SUSPEND and `window.job_inhibit_reason(name)`, which names the layout's machine (`JOB_INHIBIT_REASON` for the CAMEO 4); GNOME suspends an idle computer on battery after 15 minutes and asks before a logout), and lets go when the job ends, however it ends. A desktop that does not agree never stops the job.
- If the daemon connection drops mid-job, show a blocking dialog with the power-button hint.

### Machine profiles in the app
The service decides which machine is on the link (`FG`, "The machine model gate"); the app follows it, names it, lays the design out on its mats and makes every job for it. For the CAMEO 4 the window reads and looks as before profiles (its texts, ranges, mat and layout; `tests/test_profile_characterization.py` and the older GUI tests hold them), except where the app now names every model: the hint under a refused machine, About, and Preferences' Model row.
- **Which machine.** `MachineMonitor` asks for the machine ping (`DaemonClient.ping_machine()`, `{"op":"ping","machine":true}`) only after a plain ping showed a service of this very build (`identity.same_build`), and only while a machine is connected or refused for its model; that reply then stands for the ping. It is ignored when it comes from another build, says `stopping`, or the request fails: the state then has no machine fields, and the service still refuses a job for another machine. `machine.machine_fields(ping)` reads it: with `connected` true, `MachineState.profile` (an id OpenCutter drives) and `support` ("tested" or "untested", narrowed to the profile's own level); with `connected` false never a profile, whatever `profile` says, but for a refused model with `support` "recognized" that support, `refused_reason` (one printable line, at most `REASON_CHARS` = 300 characters) and `recognized` (the registry id it names); unknown ids give nothing. `MachineState.choice` is the layout's machine; `detected` (the connected profile, else None), `machine_profile` (detected, else the choice's), `name`, `holders` and `holder_label(n)` ("Tool 1", or "Tool" on a one-holder model) follow it. `tools` is one ESC 15 code per holder (an N-tuple), read with the profile's grammar and dropped when the profile changes; a well-formed reply the holders cannot read (on a one-holder model, a code in the slot no holder owns) fails closed: `tools` stays None, `tools_reply` keeps the reply, the Tool rows and card show "Unclear reply" with it, and Send and Test Cut say why (`MachineState.tools_problem`) instead of waiting; `tool_code`, `tool_text`, `status_text` and `ready` use the profile's tables and status digits.
- **Texts.** The texts that name the machine are functions of its name: `another_program`, `another_program_at_start`, `switch_off_on`, `not_paired`, `another_version`, `released`, `disconnecting`, `not_disconnected_busy`; those that say to switch the machine off and on take `power_cycle` (`MachineProfile.power_cycle_to_connect`) and say something else without it. `texts_for(profile)` gives the keyword arguments; `reason_problem` and `startup_problem` take `name=` and `power_cycle=` (`STARTUP_PROBLEMS` also matches "No paired Portrait was found" and "No paired CURIO was found"). The module constants are these texts for the CAMEO 4, word for word as before. While no machine is connected they name the layout's machine; after Disconnect, the one that was released. `power_cycle_to_connect` is set on every model where it was not observed (the safe advice); only `machine.power_cycle_seen(profile)` (the tested CAMEO 4, where it was seen) lets a text say as a fact that the machine accepts a connection only right after it is switched on, and the others get the advice alone. Elsewhere the same: `connection.power_on_hint(name, seen)`, `firstrun.switch_on_step(profile)`, `connect_hint(name, power_cycle)`, `release_hint(name)`, `state_hint(state)`; `window.job_inhibit_reason(name)`. `WRONG_MODEL` and `WRONG_MODEL_UNKNOWN` stay as they are; a refused machine that reports a name several models share (`CAMEO V1.10`: a CAMEO 1, or a CAMEO Pro MK-II with some of its settings; `machines.detect`'s `Detection.shared`) gets `SHARED_MODEL`, which says that OpenCutter cannot tell which model it is.

## Packaging

OpenCutter is released as a Flatpak bundle, `opencutter-<version>.flatpak`, attached to each
GitHub release; it is not on Flathub. README.md ("Install") says how to install it, CONTRIBUTING.md
how to build it locally and how to release.

- **Manifest.** `build-aux/flatpak/io.github.mortyniners.OpenCutter.yml`: app id `APP_ID`, runtime
  `org.gnome.Platform//51` with the SDK `org.gnome.Sdk//51` (Python 3.14, PyGObject 3.58, GTK 4.24,
  libadwaita 1.10; OpenCutter needs GTK 4.20, libadwaita 1.8 and PyGObject 3.50 or newer), command
  `opencutter`.
- **Permissions** (`finish-args`), each for one reason: `--socket=wayland`, and
  `--socket=fallback-x11` with `--share=ipc` (the window; X11 only where there is no Wayland, and
  X11's shared memory needs the IPC namespace); `--device=dri` (GTK 4 draws with the GPU);
  `--system-talk-name=org.bluez` (the service finds the paired machine in BlueZ and holds its
  Bluetooth LE link; nothing else on the system bus). No network and no file access: designs come
  in through the file chooser portal (**Open**) or the file transfer portal (drag and drop), and
  the app keeps no file paths between runs. Its settings, presets file and service log are in
  `~/.var/app/<app id>/`, where Flatpak points `$XDG_CONFIG_HOME`, `$XDG_DATA_HOME` and
  `$XDG_STATE_HOME`. Flatpak sets `$XDG_STATE_HOME` only from 1.14 on; without it,
  `client.state_dir()` uses the same `~/.var/app/<app id>/.local/state` inside a sandbox
  (`--persist=.local/state` would not do: Flatpak 1.16.6 mounted `--persist=.ptest` but not
  `--persist=.local/state`).
- **Python modules.** One module per package, each one PyPI release file pinned by URL and sha256
  and installed offline (`pip3 install --no-index --no-build-isolation`): poetry-core (only to
  build dbus-fast; removed after the build), dbus-fast from its sdist with the SDK's Cython (the
  build fails when its compiled extension is missing, rather than falling back to pure Python),
  bleak as its `py3-none-any` wheel (its sdist needs the `uv_build` backend, which the SDK does
  not have), svgelements from its sdist (its stray top-level `test` package is removed). PyGObject,
  GTK and libadwaita come from the runtime. To move a pin, take the file's URL and sha256 from
  `https://pypi.org/pypi/<name>/<version>/json`.
- **The app module** builds the repository itself (a `dir` source: the folder two levels above the
  manifest), without `.git`, `.venv`, `tests` and build output (also `build` and `dist`, where a
  `pip install .` in the working copy leaves files that pip would reuse), and installs the package
  with pip (the in-app icons are package data). A smoke test follows in every build, CI's
  included: `opencutter --version` runs, the GUI and service modules import, and the style sheet
  and the three icons are installed. Then the desktop file, the metainfo, and the app icon and its
  symbolic variant go into `/app/share` for the desktop. A local build takes the working copy as
  it is (uncommitted and git-ignored files too); a bundle for others is built from a clean clone.
- **The service in the sandbox.** The window starts the background service through the Flatpak
  portal (`flatpak-spawn`), in a sandbox of its own with the same permissions, so that it outlives
  the window: see "Inside Flatpak" under "The background service".
- **Release workflow.** `.github/workflows/flatpak.yml` has three jobs. The test job runs the test
  suite on Python 3.14 (the runtime's), with exact versions of pytest and of the app's dependencies
  (those the manifest installs), wheels only, and PyYAML, but without PyGObject:
  `tests/conftest.py` then skips the tests that need GTK. The build job builds the bundle with
  `flatpak/flatpak-github-actions/flatpak-builder` in Flathub's `gnome-51` container image (the
  GNOME 51 SDK and runtime are in it), from scratch (no cache). Both run side by side for pushes to
  `main`, pull requests and Run workflow (the bundle is an artifact of the run) and for tags `v*`.
  For a pushed tag, the release job runs only when both have passed, so a failed test releases
  nothing. It is the only job with `contents: write` (the workflow is `contents: read`), and it
  checks with `build-aux/release-version.py --tag` that the tag is `v` + the version of
  `pyproject.toml`, `opencutter.__version__` and the newest metainfo `<release>` (a release: X.Y.Z,
  `stable`), then creates the GitHub release with the bundle and `SHA256SUMS` in one `gh release
  create` (a draft until both files are uploaded, so a release is never public without its bundle,
  which immutable releases would make permanent), or adds them to a release made by hand. A bundle
  already attached is never replaced (a rebuild is not byte-identical); only a `SHA256SUMS` whose
  bundle never arrived is. The bundle is for x86_64 only. The build job makes the same version
  check before it builds, so a wrong tag fails early. Every action is pinned to a full commit SHA,
  with its version in a comment.

## Testing rules (every contributor)

- **Never touch a real machine.** No Bluetooth, no `bluetoothctl`/`busctl`/`btmon`, no connection to the real service socket (`$XDG_RUNTIME_DIR/app/<app id>/opencutter.sock`) or to the real `$XDG_RUNTIME_DIR/opencutter.sock` of an older build, nor to `cameo4.sock`, the socket of the legacy prototype daemon. Code that stops a service (the shutdown op, the guarded SIGTERM, `opencutter service stop`, the app's replace) runs only in a private `$XDG_RUNTIME_DIR`, against stand-in services the test started itself.
- Any test that imports `opencutter.device` must first install the stub `bleak`/`dbus_fast` modules from `tests/stubs.py`, and must use a temporary socket and lock path.
- Do not launch the GUI on your display. For visual checks use `GDK_BACKEND=broadway` with `gtk4-broadwayd` on a free display number, or build the widgets without showing them.
- Tests use only the files of the repository and synthetic data. Nothing in `src/` or `tests/` reads, decrypts or redistributes Silhouette Studio files, firmware or data.
